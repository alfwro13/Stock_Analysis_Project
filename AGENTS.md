# AGENTS.md — Quantamental Portfolio Dashboard

This file provides AI coding agents with the context needed to work effectively in this codebase.

---

## Project Overview

A self-hosted **FastAPI** web application that merges quantitative analysis, fundamental analysis, machine learning, and tail-risk management into a single portfolio dashboard. It is a hobby/personal project, not a production investment platform.

- **Server:** FastAPI + Uvicorn on port `8090` (configurable)
- **Language:** Python 3.10+
- **Templates:** Jinja2 HTML (server-rendered), with Plotly.js charts and DataTables via AJAX
- **Entry point:** `python main.py`
- **Database:** SQLite at `data/analysis.db` (WAL mode)
- **Scheduler:** APScheduler (runs inside the process — no external cron)

## Key Architecture Rules

1. **Dual-storage:** Relational metadata → SQLite. Heavy time-series → Parquet. Never swap these.
2. **Self-healing:** If Yahoo Finance fails, fall back to local Parquet/JSON cache — never crash the server.
3. **Priority arbitration:** Portfolio/Watchlist/Account Transactions > LSE universe > US universe. The daily fetch universe (`data_engine.py:get_all_tickers()`) unions `accounts_engine.get_combined_holdings()` (built-in Trading accounts + Ghostfolio when enabled), the Watchlist account (`database.get_watchlist_tickers()`), every ticker in `account_transactions` across all account types (excluding the Pension synthetic `PENSION-{id}` ticker), and every enabled `market_ticker_registry` row's `ticker` and `future_ticker` (Markets page indexes/commodities/FX/rates) — so Portfolio/Watchlist/Accounts and the Markets page share one nightly fetch/quant-scan/ML-training/sentiment/tail-risk universe (added 2026-07-12; non-equity tickers have NULL fundamentals and are handled by each consumer's existing NULL-handling path, e.g. the ML ensemble's cross-sectional median imputation — see `assets/ML_MODEL_DOCUMENTATION.md`). A newly-bought unknown ticker also gets an immediate one-off fetch (`fetch_and_save_single_ticker`) as a background task, so it doesn't wait for the next 22:00 run. Delisted tickers are appended to `freetrade_blacklist.json` automatically.
4. **No LLM for sentiment:** Market sentiment uses FinBERT locally. `ai_engine.py` generates prompts for *external* LLMs but is not itself an LLM.
5. **APScheduler only:** Do not introduce external cron jobs. All scheduled work is wired through `scheduler_engine.py` (APScheduler setup, `reload_scheduler`, `start_scheduler`). Job runner functions live in `scheduler_jobs.py`; the job manifest and label helpers live in `scheduler_manifest.py`; the Workflow Monitor graph logic lives in `scheduler_monitor.py`. All three are re-exported from `scheduler_engine` so external callers need not change their imports.
6. **CSRF + session auth:** All POST endpoints are protected. Session cookies only. See `auth.py`.
7. **Workflow manifest:** Every `scheduler.add_job(... id=X)` must have a matching `JOB_GRAPH` entry in `scheduler_manifest.py` declaring its `produces`/`consumes` data artifacts (dynamic ids matched in `_resolve_manifest`). The Workflow Monitor derives its dependency graph and conflict detection from these; the manifest-completeness test fails if a registered job is missing.
8. **One canonical name per feature — no mixed terminology.** Every scheduled job, engine, page, tool, metric, signal, config option, and feature has exactly **one** user-facing name, and that *same* wording must be used everywhere it appears: the Settings UI (configuration panels **and** the Master APScheduler Matrix), the Workflow Monitor, the System Diagnostics panel, the glossary (`templates/glossary.html`), the asset docs (`assets/`), and the `README.md`. **Never invent a new display name in one place when the thing is already named elsewhere, and never show a code-derived name (e.g. a config key like `ML_TRAINING` rendered as "Ml Training") in one surface while a descriptive name is used in another.** When you add or rename anything user-facing, grep the whole app for the old/related wording and update every surface in the same change. If a single Settings panel controls several jobs (or one job spans several panels), that mismatch must be resolved — not papered over with ad-hoc per-place variants.

   **For scheduled jobs the single source of truth is `scheduler_manifest.JOB_GRAPH[job_id]["label"]`** (re-exported as `scheduler_engine.JOB_GRAPH`; it equals the Settings panel wording). Surfaces that are keyed by config key (the Master Matrix, the diagnostics last-run map) must resolve their display text through `scheduler_engine.CONFIG_KEY_TO_JOB` + `job_label()`/`scheduler_display_names()` — never by title-casing the config key. The Active-Jobs panel name comes from `_mark_job_started(job_label("<job_id>"))`, never a hardcoded literal. **Code identifiers (job ids, `run_*` functions, config keys, engine module/class names) are deliberately *not* renamed to match** — instead, every engine module whose code name differs from its GUI name carries a top-of-module comment `# GUI name: "<name>". Canonical scheduled-job names live in scheduler_manifest.JOB_GRAPH.` so a reader knows what the user calls it. Add that comment whenever you create a job whose code name differs from its GUI label.

9. **All notifications go through the unified router.** Every user-facing notification — scheduled-job status and all alerts — must be dispatched via `notification_engine.notify(source, message_type, message_text, ...)`. Do **not** call `nextcloud_talk.send_text_message()` or `INSERT` into `system_notifications` directly from a feature engine. Per-source channel routing (log file / in-app / Nextcloud Talk) lives in `NOTIFICATION_ROUTING` (`config.json`), is editable in the Settings **Notification Settings** panel, and falls back to each source's default in `notification_engine.NOTIFICATION_SOURCES`. A new alert source must be added to that registry (with a canonical `label` and parent `job_id`); a new scheduled job automatically gets a routable status row. Dedup/cooldown stays in the engines (`alert_state`) — the router only decides *where* a fired event goes. Exceptions: deep pipeline-progress chatter may still call `database.log_notification()` directly (in-app only), and file-attachment dispatches (the Fear & Greed chart) keep their own upload path gated by their enable toggle.

10. **Background jobs must never starve the web-server thread pool.** APScheduler jobs run in a thread pool shared with (or adjacent to) the threads that serve synchronous FastAPI route handlers. Any `time.sleep()`, long network retry, or other blocking call made **while holding a lock that is also acquired by web-request code paths** will prevent those threads from making progress, exhaust the pool, and make the site unresponsive — exactly what a `threading.Lock` held during 429 backoff does to `yahoo_engine._yf_singleton_lock`.

   **Rule:** Never sleep or block inside a lock that web-request threads also need. The correct pattern:

   - On the blocking condition (e.g. HTTP 429), trip a global `threading.Event` circuit breaker (clear it) and spawn a daemon thread for the actual sleep; the calling thread raises and exits the lock immediately.
   - Any thread that wants the shared resource calls `event.wait()` **before** acquiring the lock — it sleeps outside the lock and wakes with every other waiter when the event is set.

   See `tools/network_engine._enter_yahoo_rate_limit` + `yahoo_engine._RateLimitAwareLock` as the canonical reference implementation for this pattern.

   **Making a blocking engine call awaitable from an `async def` route:** if a synchronous engine function does real network I/O and the caller (an HA-integration button, a JS action awaiting the response) needs the work actually done before the response is used, wrap it with `starlette.concurrency.run_in_threadpool` rather than `background_tasks.add_task()` — the latter is fire-and-forget and is correct only when nothing downstream depends on completion. `POST /api/accounts/refresh-now` (`api_routes_accounts.py`) is the reference implementation: it used to fire-and-forget, which let the HA integration's own immediate re-poll race ahead of the backend fetch and made the "Refresh Data" button look broken even when the refresh had worked.

11. **Bootstrap 5 front-end on `base.html` — migration complete.** Every page `{% extends "base.html" %}` — never duplicate the `<!DOCTYPE>`/`<head>`/navbar boilerplate. `templates/navbar.html` has been deleted; the Bootstrap navbar lives entirely in `base.html` with active-link detection via `request.url.path`. The UI is Bootstrap 5.3 (dark via `data-bs-theme="dark"` plus CSS-variable overrides in the theme layer at the top of `static/css/styles.css` — no Sass build). Front-end libraries (Bootstrap, jQuery, DataTables + Responsive, Plotly) are **vendored** under `static/vendor/` and served locally; do not add CDN `<script>`/`<link>` tags.

    **New page checklist:**
    - `{% extends "base.html" %}` — fill blocks: `title`, `extra_head` (Plotly if needed), `body_class`, `container_class`, `content`, `scripts`.
    - All CSS in `static/css/styles.css`; no inline `style=` attributes (exception: JS-generated `innerHTML`). Check for an existing class before adding one.
    - JS blocks > ~50 lines with no Jinja → `static/js/<page>.js` loaded via `{% block scripts %}`; use a tiny inline bootstrap for `window.*` Jinja globals. Never put `{{ }}` in a `.js` file.
    - Tables use `<table class="table table-hover w-100">` with DataTables `responsive: true` and per-column `responsivePriority`. For JS-rendered tables (rows built by `fetch()`) keep a plain `<table>` with Bootstrap classes rather than DataTables.
    - Use Bootstrap grid (`.row` + `.col-12 .col-lg-*`) and spacing utilities; avoid custom layout grids where Bootstrap breakpoints suffice.

15. **Never let a fetched value die with the engine that fetched it — share it via a timestamped cache.** Any engine that fetches external data (Yahoo Finance price/OHLCV, macro data, news, etc.) for its own narrow purpose must also persist any generally-useful derived value (e.g. a ticker's current price) to a shared, timestamped cache table, so other engines and pages can reuse it instead of re-fetching. Before writing new fetch logic for something another part of the app already tracks, check the relevant shared cache first (with a freshness/staleness check) and only fetch if it's missing or stale — never fetch unconditionally just because it's convenient for the caller.

    The canonical example is live/current price: `market_pulse_cache` (`market_pulse.py`) is the single shared cache — `market_pulse.upsert_live_price()` writes to it, `market_pulse.get_cached_pulse_from_db()`'s `needs_refresh` flag is the check-before-fetch read path. The Crash & Moonshot scan (`intraday_orchestrator.py`) and Dip Radar (`intraday_bottom_engine.py`) both write into it from data they already fetch for their own pattern detection; the Portfolio page (`page_routes.portfolio_page`) and the `/api/market-pulse` JS-polling loop both read from it, and — added 2026-07-08 — the Portfolio page now also self-triggers a `fetch_and_save_pulse()` background refresh for any stale held ticker on every load, via the same `api_routes_accounts.maybe_trigger_price_refresh()` the Home Assistant-polled JSON endpoints already used, rather than passively waiting on the next scan cycle. Neither of the two heavy scanners re-fetches from this cache themselves — they need actual OHLCV bars at a specific resolution their own pattern math requires, which a single cached price can't substitute for — but they never discard the price they derive along the way.

    **When adding or materially changing an engine that fetches external data, or when you notice one engine re-fetching something another engine already holds fresh:** wire the new engine into the existing shared cache (extending it if the existing schema doesn't fit) rather than adding another isolated fetch-and-discard path. Flag it as a bug if a code review finds a fetch that duplicates data another engine already has timestamped in a shared table.

    **Retention for a shared cache must be orphan-aware, not purely age-based, when the thing being cached can legitimately go stale for a long, predictable stretch (a market closed for a weekend/holiday) without actually being wrong.** A blind age cutoff in a periodic cleanup job (e.g. the weekly `maintenance_job`'s `prune_pulse_cache()`) will delete a value nobody intends to refresh yet, and if the same value's normal refresh path is *also* gated on the same "is the market open" condition, the two gates compound: the value can never come back on its own until the market reopens. When adding an age-based prune to a shared cache, check whether anything reading that cache also gates its own refresh on the same real-world condition the age cutoff is meant to approximate — if so, the prune must exempt currently in-scope keys (portfolio/watchlist/fixed lists/etc.), not just soften the age threshold. See `maintenance_engine.prune_pulse_cache()` (exempts tickers from `_get_pulse_active_tickers()`) and `accounts_engine.tickers_needing_refresh()` (bootstrap exception for a ticker with zero cached rows) for the fix that closed this gap on `market_pulse_cache` (2026-07-05).

    **A second canonical example is next earnings date:** `stock_signals.next_earnings_date` is written nightly by the Quant Scan (`quant_signals.py`) and weekly by the Universe Fundamentals sync (`universe_fundamentals_engine.py`), both from Yahoo's `info['earningsTimestamp']` field. Any feature checking "does this ticker have earnings soon" — `earnings_engine.py`'s earnings-day alert, `earnings_vol_engine.py`'s Earnings Volatility scan — must read this column via the shared `db_helpers.get_next_earnings_dates()` helper rather than re-deriving the date with a live `yahoo_engine.get_ticker_info()`/`get_earnings_dates()` call. Found 2026-07-12: `earnings_vol_engine.py` was independently live-fetching this exact value for every Portfolio/Watchlist ticker on every run — regardless of whether that ticker had near-term earnings — causing avoidable Yahoo rate-limit hits (52 in one run) that a single cheap SQL pre-filter eliminated.

16. **One canonical function per shared calculation — never recompute the same concept independently in multiple places.** This applies to derived business math, not just raw fetched values (rule 15 covers the latter). If two or more features need "the current price for a ticker," "P&L for a position," "an FX conversion," etc., there must be exactly **one** function that computes it, and every caller uses that function — not a parallel reimplementation with its own logic for freshness, fallback, or edge cases.

    **Bypass to flag as a bug:** a new page/engine/endpoint writing its own inline logic to derive a value that an existing engine already computes (e.g. picking a "current price" from `market_pulse_cache` vs. `stock_signals` with bespoke freshness rules, when `accounts_engine.current_price_map()` already does this canonically). Independent reimplementations drift apart over time even when they start out equivalent, and the divergence is invisible until two pages are compared side by side — see the Portfolio/Stock Detail/Accounts price-consistency bug (fixed 2026-07-03) where three separate "get the current price" implementations had quietly diverged.

    **Before writing new calculation logic:** grep for the concept first (e.g. `current_price`, `exchange_rate`, `pnl`) to check whether a canonical engine function already exists. If it does, use it. If a genuinely new calculation is needed that overlaps with an existing one, extend the existing canonical function rather than writing a sibling.

    | `table_columns_helpers.py` | Declarative registry of every Portfolio/Watchlist table column (core + optional) and named column-preset Views, plus per-row value formatting — the single source of truth `column_picker.js` and both page templates read from, so column order/keys never drift between them | `OPTIONAL_COLUMNS`, `all_columns_for_page`, `build_optional_column_cells`, `resolve_column_prefs`, `resolve_views` |
    | `static/js/utils.js` | Small, generic, cross-page front-end JS helpers with no page-specific dependency (the front-end equivalent of `utils.py`) | `escapeHtml()`, `applyStickyTheadOffset()` |

    **Front-end helpers follow the same rule, not just Python ones.** Before adding a small utility function (HTML escaping, string/number formatting, etc.) to a page-specific file under `static/js/`, check `static/js/utils.js` first. Any template loading a script that calls into it must add `<script src="/static/js/utils.js?v={{ css_version }}">` before that script tag. `static/js/utils.js` consolidated four byte-for-byte-identical `_escapeHtml`/`_wlEscapeHtml` copies (`accounts.js`, `watchlist_account.js`, `stock_detail.js`, `watchlist_add_ticker.js`) on 2026-07-12.

    **Before writing a new utility function, calculation, or query helper:** grep the relevant helper file(s) above for the concept first. If an existing function already does it, or is close enough to extend (e.g. an extra parameter), use/extend it — do not write a second, parallel implementation in the calling module. Same failure mode as rule 16, generalised beyond business calculations to any reusable helper: duplicated logic drifts apart silently (a fix applied to one copy doesn't propagate to the other) until two callers disagree on something that should be identical — see the `get_mutual_fund_tickers()` gap (fixed 2026-07-03) where `intraday_orchestrator.py` had its own undocumented ad-hoc `ticker.startswith('0P')` mutual-fund check instead of using the canonical `db_helpers` function, which itself hadn't been wired into every `get_intraday()` call site that needed it.

    **Search by purpose, not exact name.** A duplicate is rarely named the same as the original — `_get_current_price`, `resolve_price`, and `latest_quote` can all be the same concept reimplemented three times. Grep for the underlying noun/verb (`price`, `pnl`, `mutual_fund`, `exchange_rate`) across the five helper files above rather than just the function name you're about to write.

    **When no existing helper file fits:** if a genuinely new domain of shared logic emerges, create a new `<domain>_helpers.py` rather than forcing it into an unrelated file or leaving it duplicated inline. Keep each helper file scoped to one concern; if it grows too large for a single Read, that's the rule 12 split signal.

18. **Uniform Plotly chart conventions.** Every Plotly chart on a Jinja page (both JS-rendered and Python-rendered via `visuals*.py`) follows the same layout skeleton, established after fixing a string of mobile/fullscreen bugs on the Account Detail chart (2026-07-04). When building or reviewing a chart, check it against all of these:

    **Title & legend**
    - Title centered: `title: { text: '...', x: 0.5, xanchor: 'center' }`.
    - Legend horizontal, positioned **below** the plot, not top-right: `legend: { orientation: 'h', yanchor: 'top', y: -0.15, xanchor: 'center', x: 0.5 }`. A top-right legend collides with the centered title on narrow/mobile widths.

    **Margins & axes**
    - `yaxis: { automargin: true, ... }` always — without it, wide tick labels (e.g. `10k`, `12k`) get clipped on the left edge.
    - `margin.b` must be large enough (≥60) to fit the below-plot legend without it being cropped.

    **Responsive height**
    - Height must not be a single fixed value. Use a small helper (e.g. `_acctChartHeight()`) returning one height under a 768px breakpoint and a taller one above it. Both the normal render path and the fullscreen path must call the same helper — don't duplicate the breakpoint check.
    - **The mobile value must be ≥400.** `static/css/styles.css` already forces `.js-plotly-plot, .plotly, .plotly div { min-height: 400px; }` under `@media (max-width: 768px)` (added for the Macro chart, well before this rule existed). A chart requesting a shorter mobile height doesn't actually get one — the container is floored at 400px by that rule regardless, but the chart's own internal SVG can end up pinned at the smaller requested value depending on how it was rendered (client-side `Plotly.react()` + `Plotly.Plots.resize()` happens to pick up the floored container size; a server-rendered chart (`fig.to_html()` from `visuals*.py`) adjusted later via a bare `Plotly.relayout()` does not), leaving a visible empty gap below the chart. This was found and fixed 2026-07-04 on the Pension/House pages after their mobile height was set to 260 — always set the mobile branch to `400`, not a smaller "looks right" number, until/unless the global floor is revisited.
    - **A height-*shrinking* `Plotly.relayout()` call does not reliably resize its own container elements.** Confirmed via live device inspection 2026-07-06 on the ETF Predictor page: calling `Plotly.relayout(plotEl, { height })` with a *smaller* height than the chart's original server-rendered height correctly shrinks `.svg-container` (the actual drawing surface) but can leave both `.plot-container.plotly` **and** the outer graph div (`plotEl`, `.js-plotly-plot`) pinned at their original, larger inline height — each independently, one level at a time, so fixing only the outer div is not sufficient. The visible symptom is dead/grey space below the chart, roughly equal to the height difference. **Fix:** after every `Plotly.relayout()` call that can shrink height, also explicitly force both elements' inline height to match: `plotEl.style.height = height + 'px'; const c = plotEl.querySelector('.plot-container'); if (c) c.style.height = height + 'px';` — do not assume `relayout()` alone propagated the new size outward. This is distinct from the mobile-floor bug above (which is about *what* height value to request); this is about the relayout call not fully applying *any* requested height reduction. Reference implementation: `static/js/etf_predictor_detail.js` (`_relayoutEtfChart`). Any other server-rendered chart whose mobile/fullscreen height can *decrease* relative to its initial render (not just increase, like the simpler fixed-height Pension/House charts) should apply the same explicit-height-forcing pattern — check when next touching such a chart, per the no-partial-compliance rule above.

    **Fullscreen button**
    - Use the **CSS class-toggle pattern** (`wrapper.classList.toggle('is-fullscreen')` + `window.dispatchEvent(new Event('resize'))`), never the native browser Fullscreen API (`requestFullscreen()`/`exitFullscreen()`). The native API was tried and abandoned on the Accounts page after repeated, unfixable bugs where exiting fullscreen left the chart corrupted (wrong axis range/zoomed, or blank) — root cause never fully isolated across several attempts, whereas the class-toggle pattern works reliably.
    - **Structural requirement:** the `.fullscreen-btn` element must be a child of the *outer* wrapper div that receives the `.is-fullscreen` class — never a sibling of, or child of, the actual Plotly target div. Plotly's `react()`/`newPlot()` fully owns and can wipe the innerHTML of its target div on redraw, so the button must live one level up.
    - On enter, relayout height to `window.innerHeight - 120` so the chart actually uses the available vertical space.
    - On exit, relayout height back to `<same responsive-height helper>`.
    - **On mobile (< 768px), hide the fullscreen button entirely** (`display: none` in the existing `.chart-wrapper`/`@media (max-width: 768px)` block) — a phone screen is already full-width, so "fullscreen" adds nothing there.

    **Server-rendered charts do not self-resize — width included.** A chart created via `visuals*.py`'s `fig.to_html()` (embedded as a raw `<script>Plotly.newPlot(...)</script>` in the page) does **not** react to its own `config.responsive: true` the way a chart created via the JS API (`Plotly.react()`/`Plotly.newPlot()` called from your own code) does. Concretely: rotating a phone from portrait to landscape, or toggling fullscreen, changes the container's width in the DOM, but the chart's internal SVG silently stays pinned at whatever width it was first drawn at — found 2026-07-04 on the Pension/House charts (rotating to landscape left the chart stuck at portrait width) after the Accounts (Trading) chart, which *is* JS-rendered, was confirmed unaffected. **Fix:** for any server-rendered chart, explicitly relayout both dimensions yourself — measure `plotEl.getBoundingClientRect().width` and call `Plotly.relayout(plotEl, { width, height })` — wired into three places: (1) once on `DOMContentLoaded`, (2) a `window.addEventListener('resize', ...)` handler (covers rotation and any other viewport change), and (3) the fullscreen enter/exit branches above (replacing a height-only relayout there). Do not assume `config.responsive` alone is sufficient for a server-rendered chart — verify by actually resizing the viewport, not just by reading the config.

    **Fullscreen implementation is centralized.** All fullscreen-capable charts share `static/js/chart_fullscreen.js` (`ChartFullscreen.toggle()` / `relayoutForCurrentState()` / `relayoutPlot()`). A page's `toggleFullscreen()` is a thin wrapper passing page-specific options (`forceWidth`, `getHeight`, `getExtraProps(isFullscreen, plotEl)`, `onEnter`/`onExit`, and `innerWrapperId` for the outer/inner wrapper variant). Reference implementations: `static/js/yahoo_api_usage.js` (single-wrapper, JS-rendered), `static/js/account_detail_house.js` (single-wrapper, server-rendered), `static/js/stock_detail.js` (single-wrapper, server-rendered, page-specific navbar/sticky-column hooks), `static/js/etf_predictor_detail.js` (outer/inner wrapper, server-rendered, mobile margin-shrink hook). A new chart page must load `static/js/chart_fullscreen.js` before its own script and call `ChartFullscreen.toggle()` — never write a bespoke implementation or the native Fullscreen API.

    **Modal-opened detail chart — for a per-row chart on a page whose results table can grow long.** Use this pattern instead of an always-visible chart embedded inline below (or beside) the table whenever the chart only makes sense for one selected row/pair at a time, not the whole table at once. An inline chart on such a page pushes down with every additional row and can end up entirely off-screen below a long table — found 2026-07-19 on the Head & Shoulders Pattern Detector, where the per-ticker pattern chart lived in an inline panel below the results table and became unreachable once enough tickers were being monitored to push it off the visible page. The fix, and the pattern to reuse going forward: a Bootstrap modal (`.modal.fade`, `modal-dialog-centered`, `modal-xl`) containing the chart in a `.chart-wrapper`/`.fullscreen-btn` pair (rule 18's fullscreen convention still applies inside the modal), opened by a row-click handler that stores the clicked row's identity, calls `bootstrap.Modal.getOrCreateInstance(modalEl).show()`, and defers the actual `Plotly.newPlot()` call to a `shown.bs.modal` listener rather than calling it immediately. **This ordering is load-bearing, not a style choice:** Plotly sizes itself from the container's rendered dimensions at the moment it draws, and a Bootstrap modal's content has zero width/height until the modal has actually finished its show transition — drawing immediately on click (before `shown.bs.modal` fires) produces a collapsed or zero-size chart. Reference implementations: `templates/pairs_spread_monitor.html` + `static/js/pairs_spread_monitor.js` (`_psmOpenChart`/`_psmLoadChart`, opened by clicking a correlated pair row to compare both tickers' indexed price history) and `templates/pattern_detection.html` + `static/js/pattern_detection.js` (`_pdOpenDetail`/`_pdLoadChart`, opened by clicking a ticker row to see its price history with the detected pattern's structural points, key line(s), and breakout overlaid — the renderer draws generically from whichever `points`/`lines` the pattern's family returned, so it needs no changes when a new pattern family is added). Use this pattern for any future per-row/per-pair chart on a table-driven page; keep a single always-visible chart (no modal) only for pages where the chart is the page's one primary subject, not a per-row drill-down (e.g. Market Regime, Monte Carlo).

    **Column-visibility implementation is centralized the same way, for DataTables columns.** Added July 2026 for the Portfolio/Watchlist "Columns" picker, extended the same month with named "Views" presets: `static/js/column_picker.js` (`ColumnPicker.resolveVisible()` — a pure function usable before `.DataTable()` is even constructed, so the initial `columnDefs` `visible` array can be computed with no flash of all-columns-visible; `ColumnPicker.init()` — wires the Columns dropdown menu and returns `{isVisible, applyView, getCurrentVisibleKeys}`; `ColumnPicker.initViewsMenu(picker, opts)` — wires a second dropdown for saving/applying/deleting named column presets, calling back into the same `picker` instance rather than maintaining separate visibility state) is the shared module both `portfolio.js` and `watchlist.js` call into, backed by the column + view registry in `table_columns_helpers.py` (rule 17). A new page adding a column-visibility picker over a DataTables instance must extend `table_columns_helpers.py`'s registry and reuse `column_picker.js` — never a bespoke per-page implementation. See `assets/configurable_columns.md` for the removed `applyFilterOverride` mechanism (a page-specific filter/column-visibility interaction, deleted once its only caller — Watchlist's `#targetFilter` — was retired in favor of Views) — don't re-add that pattern without a concrete second caller.

19. **Alert dedup gates must never auto-fire solely because a calendar day rolled over.** `IntradayOrchestrator._evaluate_alert_gate()` (`intraday_orchestrator.py`) is the shared dedup/cooldown ledger (`alert_state` table) behind every *condition-severity* alert engine — Crash, Moonshot, AI Contagion, Trap Monitor, HMM Regime, Market Stress, and Macro. A repeat alert for the same ticker/engine/condition must require either (a) a genuinely new condition class (the reason's fingerprint changed), or (b) cooldown elapsed **and** measurable worsening since the last fire. A UTC-date check alone is not a valid firing condition for these engines, even as a "first scan of the day" special case.

    **Composite key for per-account (not just per-ticker) conditions:** `alert_state`'s primary key is `(engine, ticker)` — one row per real ticker per engine. An engine whose condition is scoped *below* ticker level (e.g. a price target that's set independently per account, or any future per-account/per-holding condition) must not reuse the bare ticker symbol as the key, since that would collapse multiple independent conditions on the same ticker into one shared dedup state. Instead, encode the extra scope into the `ticker` column as a composite string (e.g. `f"{account_id}:{ticker}:{direction}"`) and pass that composite value everywhere the gate function expects a ticker — no schema change needed, since the column is plain `TEXT` with no FK. **HoldingLimit** (below) is the reference implementation for this composite-key pattern.

    **Exception — HoldingLimit's and AI Contagion's daily gate is a deliberate, explicitly-requested departure from (b) above.** A price target (Position Targets / Set Targets) is a static threshold, not a severity condition — the price can legitimately oscillate back and forth across it several times in one session, and re-notifying on every crossing (or even on a worsened-price retrigger the way Crash/Moonshot does) was found to be noise, not signal. Per explicit user direction (2026-07-10): **at most one notification per (account, ticker, direction) per UTC calendar day**, re-arming automatically at the next day's rollover regardless of price recovery. This is implemented as a **separate, purpose-built method**, `IntradayOrchestrator._evaluate_daily_alert_gate(engine, key, conn, max_per_day=1)` — not a branch inside `_evaluate_alert_gate` — because the semantics are fundamentally different (no fingerprint, no worsened/recovered, no cooldown-minutes config; just "has this engine/key already fired `max_per_day` times today, via `alert_state.fire_count`"). It still shares the same `alert_state` table and the same composite-key pattern (`{account_id}:{ticker}:low` / `{account_id}:{ticker}:high`, via `_check_holding_limits()`) and the same `record_alert_fired()` write path. **AI Contagion** (`run_ai_contagion_job()`, `scheduler_jobs.py`) also uses this gate as of 2026-07-13, with a user-configurable `NOTIFICATIONS.AI_CONTAGION.MAX_ALERTS_PER_DAY` (Settings → AI Sector Contagion Monitor → "Max Alerts Per Day", default 1) instead of the hardcoded `max_per_day=1` HoldingLimit uses — a rolling `COOLDOWN_MINUTES` window let an alert fired near market close only re-arm ~24h later, near the *next* day's close, drifting later each day rather than resetting at a fixed point; a fixed UTC-midnight reset was explicitly requested instead. Unlike HoldingLimit's composite per-account key, AI Contagion keys the gate on the engine's existing synthetic `ticker="SECTOR"` (one shared cooldown slot for the whole sector, not per-ticker — see `ai_contagion_engine.py`). **Do not generalize this exception further** — a new engine wanting date-based dedup must have an equally explicit reason (a static, user-set threshold, or an explicit user request to avoid a drifting rolling window, rather than a computed severity score); default to the `_evaluate_alert_gate()` worsened/recovered/cooldown model for anything else.

    Found 2026-07-08: an earlier version of the gate treated "no dedup row yet for today's UTC date" as sufficient reason to fire, regardless of whether the underlying score/price had changed since the alert last fired. Proof from `system_notifications`: a Trap Monitor alert for META fired at 07:00 UTC on five consecutive trading days with byte-for-byte identical text (same RSI, same EMA distance) — the daily scan was genuinely fresh, but was scoring an unchanged EOD daily bar (no new bar forms until that day's close), so the "new day" reset alone produced a spurious repeat every single morning. This is why Trap Monitor's gate call now passes `ema_distance` (a real magnitude) instead of `None` — an engine with no live price still needs *some* numeric severity value passed into the gate so genuine within-phase worsening can be distinguished from a stale re-run of yesterday's result. An engine that cannot supply any such value will simply stay silent until its fingerprint (condition class) changes — that is correct behavior, not a gap to patch with a day-based fallback.

20. **Dependency updates are CI-gated, documented, and self-verified at runtime.** Added 2026-07-15 after an audit of Dependabot's weekly `requirements.txt` PRs found none of this existed.

    **CI:** `.github/workflows/tests.yml` runs `./run_tests.sh` (the full suite) on every push to `main` and every pull request — including Dependabot's. A Dependabot PR's checks tab is the first thing to look at before merging; don't re-derive test results by hand if CI already ran them.

    **Per-package usage/risk reference:** `assets/dependencies.md` documents what each `requirements.txt` entry is actually used for and what to test after upgrading it (e.g. ML libraries carry a silent-accuracy-drift risk rather than a crash risk; `joblib` carries a pickle-compatibility risk with existing `models/*.joblib` artifacts). Keep it current — when adding, removing, or changing what a dependency is used for, update this file in the same change, the same way `assets/api_reference.md` is kept current for endpoints.

    **Dependabot grouping:** `.github/dependabot.yml` groups related packages (web-framework, market-data, charts-templating, ml-ai) for minor/patch bumps only; major-version bumps always arrive as individual, ungrouped PRs, since a major bump is exactly the case that needs its own focused review.

    **Startup drift detection:** `utils.check_requirements_drift()` / `notify_requirements_drift()`, called from `main.py`'s lifespan on every boot, compares installed package versions against `requirements.txt` pins and notifies via `notification_engine.notify("system_update_status", ...)` on mismatch. This exists because the pre-existing reinstall path — `api_routes_system.py`'s git-pull sets `_requirements_changed_pending`, an in-memory global, which `execute_restart()` consults before running `pip install -r requirements.txt` — only survives a restart that goes through the Settings "Pull Latest from GitHub" + Restart buttons. A crash, `systemctl restart`, a server reboot, or a manual `git pull` on the server all silently drop that flag, leaving the venv permanently out of sync with `requirements.txt` with no other signal. The startup check is detect-and-notify only — it does not run `pip install` automatically, to avoid adding a network call and installer run to every boot.

## Testing

Run the full regression suite once, at the end of the task, before marking work done:

```bash
./run_tests.sh              # full suite (~3400 tests)
./run_tests.sh --fast       # skip slow page-render tests
./run_tests.sh --db-only    # DB schema tests only
./run_tests.sh --api-only   # API endpoint tests only
```

One full run per task is sufficient — do not re-run the full suite after every individual fix within a multi-fix task. `.github/workflows/tests.yml` already runs the full suite on every push to `main` and every pull request (see rule 20), so a pushed/PR'd change gets a second independent run regardless; running it repeatedly locally mid-task mostly burns time (~10 minutes a run) without adding coverage the final local run and CI don't already provide. If you're actively debugging a specific failure and want a fast local signal before the final full run, `./run_tests.sh --fast` or a targeted `pytest tests/test_foo.py` is cheaper than a full run — use judgement rather than defaulting to the full suite on every step.

Tests live in `tests/`. Fixtures and the test client are in `tests/conftest.py`. Do not mock the database in tests — the suite uses a real in-memory SQLite instance spun up per session.

A new `run_*` job-runner function in `scheduler_jobs.py` must have at least one test that calls the runner itself (e.g. `scheduler_jobs.run_foo_job()`), not only the engine function it delegates to. A test that only exercises `some_engine.do_thing()` will not catch a missing import or wiring bug in the runner that wraps it — exactly the kind of gap that let a `NameError` slip into `run_account_value_snapshot()` undetected until a direct runner-level test was added (June 2026).

## Coding Guidelines for Agents

- **Do not add comments** unless the why is genuinely non-obvious.
- **Do not add error handling** for scenarios that cannot happen — trust framework guarantees.
- **Do not create new files** unless strictly necessary; prefer editing existing modules unless the existing files have grown to big in which case consider all options for splitting them into smaler ones
- **Do not introduce abstractions** beyond what the task requires.
- **Run `./run_tests.sh`** once at the end of the task and fix failures before marking work done — see the Testing section for why not more often.
- **Tooltips:** Use `<abbr title="Explanation text.">Label</abbr>` — wrap the label itself, no custom JS tooltip systems, no icon, no `style` attribute on the `<abbr>`. The global CSS in `static/css/styles.css` already applies `text-decoration: underline dotted #666`, `cursor: pointer`, and `color: inherit` to all `abbr` elements. Never override these inline. Keep tooltip text to 1–2 sentences matching existing examples (e.g. Support 1, RSI, ATR).
- **Styles belong in `static/css/styles.css`:** Do not write inline `style="..."` attributes. Check whether a CSS class already exists before adding anything. Only use inline styles in JS-generated HTML (e.g. dynamic `innerHTML`) where class-based styling is impractical, and even then keep it minimal.
- **No hardcoded `font-size` values for UI layout elements in `styles.css`.** All user-visible text sizes must reference a CSS custom property declared in the `:root` block (e.g. `font-size: var(--font-size-body)`). The ten variables are `--font-size-nav`, `--font-size-table` (screener/report tables), `--font-size-dt-table` (Portfolio/Watchlist DataTables — uses an explicit `td`/`th` rule, not inheritance), `--font-size-form`, `--font-size-btn`, `--font-size-section`, `--font-size-body`, `--font-size-h1`, `--font-size-h2`, `--font-size-h3`; their runtime values come from `GET /api/ui-theme.css` which reads `UI_PREFERENCES` from `config.json`. Exception: intentional data-visualisation sizes (large numeric KPI tiles, score displays, chart annotation text) may use explicit `px` values when they are purposely non-configurable.
- **Large JS blocks belong in `static/js/`:** If a template `<script>` block exceeds ~50 lines, extract it to a `.js` file (see `templates/watchlist.html` / `static/js/watchlist.js` as the reference). Use a small inline bootstrap to expose any Jinja-derived values as `window.*` globals, then load the external file with `<script src="/static/js/file.js?v={{ css_version }}">`. Never put `{{ ... }}` Jinja interpolations inside `.js` files.
- **Tables use DataTables Responsive:** New or migrated data tables initialise DataTables with `responsive: true` and explicit per-column `responsivePriority` so the full column set shows on desktop and only the essentials survive on a phone (collapsed columns move to the expandable child row). Keep the client-side full-array data load — do not switch to server-side processing. See `static/js/watchlist.js`.
- **UK market quirks:** LSE-listed stocks may have prices quoted in pence (GBX), not pounds (GBP). The codebase handles this explicitly — do not remove or simplify that logic.
- **Secrets:** All credentials live in `.env` (loaded via `python-dotenv`). Never hard-code tokens or API keys. Never commit `.env`.
- **Port:** Default is `8090`. Do not change it without updating `config.json` and `config.py`.
- **Never mask bad data in the display layer.** If a chart, table, or API response shows incorrect values due to corrupt or misformatted data in the database, the fix must go to the source — either the data pipeline (engine) or a data migration in `db_schema.py:migrate_db()`. Do not add filters, clamps, or guards in `visuals.py`, template code, or API serialisation to hide the bad values. Filtering in the display layer hides the problem from monitoring and leaves incorrect data in the DB silently corrupting other consumers (e.g. `regime_engine.py` reads `us_cpi_inflation` directly for macro regime classification).

### Time and Timezone Rules

All time-related code **must** go through `time_engine.py`. Never hardcode timezone strings, market hours, or reset times anywhere else in the codebase.

**Storage:** Always store datetimes in UTC (SQLite text as `"%Y-%m-%d %H:%M:%S"`, Parquet as naive UTC timestamps). Never store local times.

**Display:** Convert to the user's local timezone at the point of display only, using `time_engine.to_local(dt)`, `time_engine.fmt_time(dt)`, or `time_engine.fmt_datetime(dt)`. These read `USER_TIMEZONE` from config automatically.

**Market-window checks:** Use `time_engine.is_market_open(exchange)` or `time_engine.market_window_utc(exchange)`. Never compare `datetime.now(timezone.utc).time()` against a hardcoded `"HH:MM"` string — that pattern is always a bug because the string has no timezone context. **Holiday calendar:** `time_engine.is_market_open()`/`is_trading_session()` are holiday-aware for every exchange in `exchange_hours.json` via `time_engine.is_exchange_holiday(exchange)`, backed by the `exchange_calendars` library (added 2026-07-13) — it vetoes a weekday+hours "open" result on a real scheduled holiday (e.g. NYSE observing July 4th on the preceding Friday). 26 of 29 exchanges have a dedicated calendar; NSE/SZSE/Euronext deliberately share a sibling exchange's calendar (`time_engine._EXCHANGE_CALENDAR_CODES`) since each genuinely follows the same trading-holiday calendar as its sibling. `market_pulse.is_exchange_open(exchange)` additionally layers live Yahoo `marketState` intraday session granularity (PRE/POST/REGULAR/CLOSED) on top for 8 exchanges (`market_pulse._MARKET_STATUS_PROXY`: NYSE/LSE/XETRA/TSE/HKEX/SSE/ASX/Euronext, refreshed by `market_pulse.fetch_and_save_pulse()` into `market_pulse_cache.market_state`) — prefer it over `time_engine` directly when you need that granularity or premarket awareness (`include_premarket=True`). `GET /api/system/market-status`, `GET /api/system/market-status/all`, and `accounts_engine.tickers_needing_refresh()` already use it. `time_engine.market_window_utc()` also sources the day's actual open/close from `exchange_calendars` for every mapped exchange (added 2026-07-13), catching early-close/half-day sessions the static `exchange_hours.json` can't represent (e.g. NYSE's post-Thanksgiving and Christmas Eve 13:00 ET closes) — the `premarket_open` key (NYSE only) is unaffected, since `exchange_calendars` has no extended-hours concept.

**Per-ticker exchange detection:** Use `time_engine.ticker_exchange(ticker, currency)` — it maps `.L`/GBP→LSE, `.DE`/EUR→XETRA, `.T`→TSE, USD→NYSE, and falls back to `HOME_EXCHANGE` for ambiguous tickers.

**APScheduler jobs:** Use `time_engine.reset_cron_trigger_params(exchange)` to generate `CronTrigger` kwargs for end-of-session resets. Always specify `timezone` in every `CronTrigger` — a trigger without a timezone is implicitly system-local and will break across DST boundaries or server moves.

**Formatting a reset time for display:** Use `time_engine.fmt_reset_time(exchange) -> str` — it wraps `reset_cron_trigger_params` + `datetime.combine` + `fmt_time` so callers never need to import `ZoneInfo` directly.

**Config keys:** `USER_TIMEZONE` (IANA string, e.g. `"Europe/London"`) and `HOME_EXCHANGE` (`"LSE"` | `"NYSE"` | `"XETRA"` | `"TSE"`) are the two user-facing settings that drive all of the above. Both live in `config.json` and are editable via the Settings UI.

**Config-driven schedule windows (`START_TIME`/`END_TIME` and similar):** the Settings UI is inconsistent about which timezone a `"HH:MM"` schedule field represents, and that inconsistency is not visually obvious — `_alerts.html` labels `AI_CONTAGION`/`TRAP_MONITOR`'s Start/End Time fields `(UTC)`, but `CRASH_ALERTS`/`MOONSHOT_ALERTS`'s equivalent fields carry no label at all, because they're meant to be entered as `USER_TIMEZONE` wall-clock time (matching the `CronTrigger(timezone=user_tz)` that fires the job — see `scheduler_engine.reload_scheduler()`). Before writing code that reads a schedule config string and compares it to `datetime.now(timezone.utc)`, check the field's UI label (or ask) to determine which timezone it's actually in — never assume a bare `"HH:MM"` config value is already UTC just because comparing it directly to UTC "now" is the path of least resistance. A local-time value must be localized via `time_engine.get_user_tz()` (combine with today's date, `.astimezone(timezone.utc)`) before the comparison. This exact bug shipped in `intraday_orchestrator.py:IntradayOrchestrator._run()`: it compared `CRASH_ALERTS.START_TIME`/`END_TIME` directly against UTC "now" with no localization, which silently delayed the Crash/Moonshot scan's first successful run of the day by the DST offset (~1 hour during BST) — and since that scan is what keeps `market_pulse_cache` warm for held tickers, it left the Portfolio page's unrealized P&L showing the prior day's close well after LSE had opened. Fixed 2026-07-08.

As of 2026-07-10, `run_account_value_snapshot()` (`scheduler_jobs.py`) also calls `accounts_engine.refresh_all_trading_performance_caches()` immediately after the snapshot succeeds, so `account_performance_cache` (period-return baselines) reflects the new trading day right away instead of staying frozen at the last `account_performance_refresh_job` cron tick (~21:59 UTC) until its 07:00 UTC window reopens.     **Watchlist row (added 2026-07-10):** the Watchlist is itself a real built-in account (`account_type='Watchlist'`, singleton, `db_accounts.get_watchlist_account()`) — `holding_price_limits` is generic on `account_id` with no Trading-only restriction, so a Watchlist target needs zero schema/endpoint changes, only a synthetic row appended to `target_accounts` in `page_routes.py`'s `stock_detail()` (`{"account_id": watchlist_account["id"], "name": "Watchlist"}`) whenever `is_in_watchlist` is true — alongside real Trading-account rows if the ticker is held in one or more. Every 5-minute intraday scan compares each ticker's live price against any set target (low fires on `current_price <= low_limit`, high on `current_price >= high_limit`) and fires a `holding_limit_alert` notification (source label "Position Target Reached") via `IntradayOrchestrator._dispatch_holding_limit_alerts()`, gated by the dedicated once-per-UTC-day `_evaluate_daily_alert_gate()` — see rule 19's HoldingLimit exception for why this engine deliberately does not use the shared `_evaluate_alert_gate()` worsened/recovered/cooldown model. **Routing is independent of Crash/Moonshot/Anomaly**, both in notification channels (its own `NOTIFICATION_SOURCES["holding_limit_alert"]` entry, so Settings → Notification Settings toggles it separately) and in scan scope: `IntradayOrchestrator._compute_target_only_tickers()` derives the set of tickers with an active target that aren't already held, and `_run()` scans them through `_check_holding_limits()` only — a Watchlist-only ticker with a target set never enters Crash/Moonshot/Anomaly evaluation, which stays scoped to `get_portfolio_tickers()` (Trading accounts + Ghostfolio) exactly as before. Scoped to built-in accounts only; a Ghostfolio-only holding has no `account_id` to attach a target to.
- **Account Price Scraper** (`account_scraper_engine.py`): generic URL + CSS-selector price feed for `House`/`Pension` accounts, added June 2026, replicating Ghostfolio's "manual asset" scraper. Configured per-account from the Accounts page (tile gear icon / detail page) — not the Settings page — via `PUT /accounts/{id}/scraper-config` (URL, selector, optional JSON headers, daily run time, enabled flag); a `Test` action validates without persisting, a `Scrape Now` action runs the saved config immediately. Each scraper-enabled account gets its own dynamic APScheduler job (`account_scraper_{account_id}_job`, registered/unregistered by `scheduler_jobs.register_account_scraper_job`/`unregister_account_scraper_job`, matched in the manifest via `scheduler_manifest._DYNAMIC_ACCOUNT_SCRAPER_RE`) at the account's own time in `USER_TIMEZONE`, with no `day_of_week` restriction. Extracted prices land in `account_price_history`. For `House`, the latest price *is* the account's equity value (`accounts_engine._equity_value_for_account`) — there is no holdings/transaction concept at all. For `Pension`, the price values a single synthetic holding represented internally as ticker `PENSION-{account_id}` (never shown in the UI) so the existing average-cost ledger needs no changes; `accounts_engine._current_price_map()` resolves that ticker from `account_price_history` instead of `stock_signals`. Two dedicated actions build that holding: `record_pension_contribution()` ("Pay In" — amount ÷ that date's price = units bought) and `record_pension_fee()` ("Admin Fee" — units-before from the ledger minus the units-after the operator reads off the provider's portal = units removed and their cost). Both create `Buy`/`Sell` rows with `update_cash=False`, since a Pension account has no cash sub-ledger.
- **UK Treasury Bills** (`treasury_bill_engine.py`): zero-coupon instrument tracking for `Trading` accounts, added July 2026. A dedicated "Buy T-Bill" action (`POST /api/accounts/{id}/treasury-bills`) posts a `Buy` transaction against a unique per-purchase synthetic ticker (`TBILL-{buy_txn_id}`) — never a shared ticker — so concurrently-held bills never blend cost basis in `accounts_engine._ledger_for_account()`'s average-cost math. Pricing is fully analytical rather than fetched: `treasury_bill_engine.accreted_price()` computes a straight-line value between the discount purchase price and face value over the purchase-to-maturity window, and `accounts_engine.current_price_map()` dispatches any `TBILL-%` ticker to it (mirroring the existing `PENSION-%` branch), so `holdings_with_market_value`, `portfolio_totals`, and the Home Assistant `holdings-list` endpoint all show the accreting value with no further changes. An always-on daily job (`treasury_bill_maturity_sweep_job`, 07:00 `USER_TIMEZONE`, no Settings toggle) posts the maturity `Sell` leg at face value and closes the position once `maturity_date` arrives; if the bill was flagged `auto_reinvest`, it fires a `notification_engine.notify("treasury_bill_reminder", ...)` reminder — **never an automatic re-purchase**, since the real yield on the next weekly DMO tender isn't known until the Friday it closes. A Treasury Bill can't be sold/edited before maturity or through the generic transaction endpoints (both `PUT`/`DELETE /accounts/{id}/transactions/{txn_id}` reject a `TBILL-%` ticker); the only way to correct a mis-entry is `DELETE /api/accounts/{id}/treasury-bills/{bill_id}`, which removes the Buy leg (and the maturity Sell leg, if already matured) together. Both `db_accounts.get_all_account_tickers()` and `accounts_engine.held_tickers_lightweight()` exclude `TBILL-%` from the Yahoo-fetch ticker universe — the latter exclusion is load-bearing here in a way it wasn't for Pension, since T-bill tickers live inside ordinary `Trading` accounts rather than a dedicated account type.
- **Backup & Recovery** (`backup_engine.py`): self-hosted backup/restore, added June 2026, configured at Settings → Backup & Recovery (right-hand column). Each run writes one timestamped `backup_YYYYMMDD_HHMMSS.tar.gz` containing any combination of `data/` (excluding `analysis.db`, via a `tarfile` member filter so the Data and Database components never overlap), `models/`, and `data/analysis.db` itself, independently toggled. Destination is a local folder (default `backups/`, gitignored) or an NFS share, mounted into a scratch mountpoint at `.nfs_backup_mount` (a sibling of `data/`, not nested inside it) for the duration of the run and unmounted afterward via two fixed root-owned wrapper scripts (`/usr/local/sbin/quant-backup-nfs-mount` / `-umount`), invoked as `sudo -n` — mounting requires root, and the app itself never runs as root, so this is delegated through a narrowly-scoped passwordless sudoers rule (operator-installed, not part of the repo) that grants only those two exact script paths, not `mount`/`umount` in general. Without that sudoers rule installed, NFS backups fail with a clean error rather than crashing; Local Folder backups are unaffected. Retention keeps the N most recent archives (sorted by filename, which embeds the timestamp). Every run — scheduled (`backup_job`, day-of-week + time) or manual ("Run Backup Now") — is logged to `backup_history` with `trigger_type` (`scheduled`/`manual`) and dispatched via `notification_engine.notify("backup_status", ...)`. Restore (`POST /api/backup/restore`, gated behind `X-Confirm-Token`) extracts the chosen archive back under `BASE_DIR`, relying on the archive's own internal paths to land correctly — destructive; the operator is expected to restart the service afterward so in-memory caches reload the restored data. **The mountpoint must never live inside `data/`:** it originally did (`data/.nfs_backup_mount`), and since the Data component's `tar.add()` walks `DATA_DIR` recursively, every run archived straight through the live mount and re-embedded the entire remote share — including every backup already stored there — into the new archive, so each day's backup recursively contained all prior ones and roughly doubled in size on every run. Found 2026-07-19 after three weeks of daily NFS backups grew a ~250MB `data/` folder into a 603GB archive; fixed by relocating the mountpoint to be a sibling of `data/` instead.
- **Alert Confidence Referee** (`alert_referee_engine.py`): a meta-labeling veto classifier, added July 2026, piloted on the Market Trap & Recovery Monitor. Distinct from the alert cooldown/dedup gate (`IntradayOrchestrator._evaluate_alert_gate()`, rule 19) — that gate stops the *same* condition re-firing; the referee instead can stop a *first-time* low-quality signal from firing at all. A `RandomForestClassifier`, calibrated with `CalibratedClassifierCV(method='isotonic')` (matching `ai_prediction_engine.py`'s calibration approach per rule 16), is trained on `trap_phase_history`'s resolved, feature-bearing rows (RSI, EMA distance, volume ratios, Bollinger width, one-hot phase) versus the phase call's actual 14-day direction outcome. `trap_phase_history` gained those feature columns in the same change — before, only the phase and its eventual outcome were persisted, not the features that drove the call, so no (features, outcome) training pairs actually existed yet despite the phase-accuracy tracking already in place.

  `alert_referee_engine.backfill_historical_features()` runs at the start of every `train_referee_model()` call (scheduled or manual) and recomputes the missing feature columns for any pre-existing `trap_phase_history` row, reloading that ticker's 2-year parquet and re-running `bull_bear_trap_engine.TrapEngine._analyse_ticker()` as of the row's own `scan_date` — so historical rows whose 14-day outcome is already resolved become usable training data immediately rather than waiting on entirely new data to accumulate from the deploy date forward. A row is only updated when the recomputed phase matches what was originally recorded (a mismatch means the parquet has since been revised, so the recomputed features would misdescribe the recorded outcome); the candidate query excludes already-backfilled rows, so repeat calls are a cheap no-op once caught up. `readiness_status()`'s `pending` count (feature-bearing, outcome not yet resolved) is a leading indicator surfaced in the Settings readiness panel for exactly this reason — added after an operator correctly pointed out that discarding the pre-existing historical phase-call history by design (rather than recovering its features) was an avoidable choice, not a hard constraint.

  Runs in one of two modes, called from `scheduler_jobs.run_trap_monitor_job()` immediately before the dedup/cooldown gate (per an explicit operator decision — a vetoed signal never touches `alert_state` and gets a fresh referee opinion on the next 5-min scan, since features may have shifted): **Shadow** mode (`alert_referee_engine.evaluate_alert()`) logs what it would have done — fire probability and would-veto flag, via `alert_referee_engine.log_veto_evaluation()` into `alert_referee_log` — without ever suppressing the alert; **Active** mode actually suppresses when the calibrated fire-confidence probability falls below the configured `VETO_THRESHOLD`. Active mode is gated server-side: even with Active configured, the referee stays in Shadow mode until `alert_referee_engine.readiness_status()` reports the resolved training-sample count has crossed the configured `MIN_TRAINING_SAMPLES` — an explicit response to there being too little historical data to trust a live veto yet, and a deliberately different design from the shared alert-gate model since the risk of suppressing a genuine rare event (the exact failure mode a threshold-based alert system exists to catch) is unacceptable to apply on the strength of a handful of samples.

  Configurable in Settings → Alerts & Reports column ("Alert Confidence Referee" card): enable, weekly training schedule (`SCHEDULING.ALERT_REFEREE_TRAINING`, own `alert_referee_training_job` scheduler job + `JOB_GRAPH` entry), mode, veto threshold, and minimum training-sample count — all four exposed as user-configurable rather than hardcoded, per explicit request. The same card shows a readiness panel (current vs. required resolved samples, and an ETA projected from the historical resolution rate) so the operator can see when Active mode will actually become available, plus a summary of the Shadow-mode evaluation log (`GET /api/alert-referee/status`) and a manual "Run Training Now" action (`POST /api/alert-referee/train`) that trains immediately regardless of the weekly schedule — training below a hard floor (`alert_referee_engine._HARD_MIN_SAMPLES`, 30) is refused outright as statistically meaningless; above that floor it always trains, but the resulting model only ever runs in Active mode once the sample count also crosses `MIN_TRAINING_SAMPLES`. Training metadata (`alert_referee_models`) and the model artifact (`models/alert_referee_trapmonitor.joblib`) are appended/overwritten per run respectively; nothing here is wired into any other engine — the pilot is scoped to Trap Monitor only.
- **Home Assistant Integration** (`Stock_Analysis_Project_ha_integration/`): a companion HACS custom component, added July 2026, that polls this app's own API to surface portfolio totals and system/market health as native Home Assistant sensors. As of July 2026 it is also published as its own independent git repository (https://github.com/alfwro13/Stock_Analysis_Project_ha_integration, with its own CI) in addition to remaining a subfolder of this repo's own checkout — it has its own `AGENTS.md` and `task_prompt.md` (the latter local-only, gitignored from its own published repo) — read both before touching anything it depends on. It currently consumes exactly 7 endpoints: `GET /api/accounts/portfolio-totals` (`portfolio_metrics_engine.portfolio_totals()`), `POST /api/accounts/refresh-now`, `GET /api/system/market-status`, `GET /api/accounts/list-with-metrics` (`portfolio_metrics_engine.account_metrics_list()` — Phase 2), `GET /api/accounts/holdings-list` (`portfolio_metrics_engine.holdings_with_metrics_all_accounts()` — Phase 3), `POST /api/accounts/holding-price-limit` (`portfolio_metrics_engine.set_holding_price_limit()` — Phase 3), and `GET /api/accounts/other-accounts-list` (`portfolio_metrics_engine.other_accounts_list()` — Phase 4, Pension/House account sensors). All 4 planned phases have now shipped. **Rule:** any change to the response schema, authentication, or behavior of an HA-integration-consumed endpoint must be checked against `Stock_Analysis_Project_ha_integration/` in the same change — additive-only field changes are safe (the integration reads fields defensively via `.get()`), but renaming/removing a field, changing an endpoint's path, or changing its auth requirements is a breaking change requiring an integration-side update (`custom_components/stock_analysis_project/api.py` at minimum, likely `sensor.py`/`binary_sensor.py`/`number.py` too) in lockstep, not a follow-up task. This also applies to the supporting infrastructure these endpoints depend on: the `account_value_history_currency` table (backs `portfolio_twr_ex_fx()`), the `account_performance_cache` table + `refresh_performance_cache()` (backs `account_metrics_list()`'s cash/equity/gain/MWRR fields), the `holding_price_limits` table (backs `holdings-list`'s `low_limit_*`/`high_limit_*` fields), the `scheduler_manifest.JOB_GRAPH["ha_refresh_now_source"]` entry, and the `notification_engine.NOTIFICATION_SOURCES["ha_refresh_now_status"]` entry. `POST /api/accounts/refresh-now` is also the canonical piggyback point for warming any *other* shared cache alongside the HA-triggered portfolio refresh — `api_routes_accounts._refresh_markets_registry()` (added July 2026) is the reference implementation: it fires `markets_engine.registry_lookup_tickers()` into `market_pulse_cache`/`market_pulse_sparkline` via `BackgroundTasks.add_task()` so it doesn't slow HA's awaited response, exactly the pattern to follow if a future feature needs its own data refreshed on the same trigger. Cross-reference: `Stock_Analysis_Project_ha_integration/AGENTS.md` (integration-side rules, the X-API-Key auth model, the coordinator/switch/number/button interaction contract, the dynamic per-item entity + config-toggle patterns, the `[NEEDS REVIEW]`-flagged coupling to `DataUpdateCoordinator` internals that must be re-verified after any Home Assistant core upgrade) and `Stock_Analysis_Project_ha_integration/task_prompt.md` (the phased Phase 1-4 build-out plan, so a future session knows what's shipped vs. planned before assuming an endpoint doesn't exist yet).

  **Always-on polling, as of 2026-07-10:** the coordinator's `_async_update_data()` no longer skips fetching `portfolio_totals`/`account_metrics`/`holdings` when both UK and US markets are closed — every poll reaches the backend regardless of market hours (`CONF_SKIP_REFRESH_WHEN_MARKETS_CLOSED` still exists but now defaults off, kept only for anyone who wants fewer polls purely to reduce load on their own server).
