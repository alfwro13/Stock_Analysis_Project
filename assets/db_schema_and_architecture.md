# 🗄️ Database Schema & Data Architecture

The Quantamental Dashboard employs a **Dual-Storage Architecture** to guarantee high performance, bypass memory bottlenecks, and prevent API rate-limit bans. It also features a dedicated **AI & Machine Learning Layer** that acts as a cyclic enricher and LLM prompt generator.

Structured metadata, fundamental metrics, and system scoring are routed to a relational **SQLite database**, while massive time-series matrices are routed to highly compressed **Parquet files** and flat JSONs.

---

## 1. The Relational Database (`data/analysis.db`)

The SQLite database acts as the central brain of the dashboard. It uses a star-like schema where most tables join on the primary key `ticker`, optimized for heavy concurrent access via WAL (Write-Ahead Logging).

### Write-Lock Handling (`db/connection.py`)

SQLite allows one writer at a time, so a write transaction that is slow to commit blocks every other writer. `db/connection.py` holds the retry connection, the write-lock registry, the deferred-write queue and the swap gate; `db/database.py` holds `get_connection()` and re-exports the public names, so callers import them from `db.database`.

* **Retry:** `get_connection()` (`db/database.py`) sets a 20 s busy timeout, and `_RetryingConnection` (`db/connection.py`) repeats a statement or commit that still fails with `database is locked` three more times with jittered backoff (about 84 s in all) before the error reaches the caller.
* **Naming the holder:** `_RetryingConnection` records every open write transaction (caller as `file:function:line`, thread, first statement, age; never parameters) and logs at `WARNING` when a transaction ends after `DB_WRITE_HOLD_WARN_SECONDS` (5 s) or more, and on the first and last failed wait of a blocked statement, naming the blocked caller and every write transaction open at that moment. `none tracked` means the holder is another process or a connection not opened through `get_connection()`. Registry entries hold only a weak reference, so an abandoned connection is never reported as a holder.
* **Deferred writes:** `db.connection.write_or_defer(description, write)` runs a self-contained write that opens and closes its own connection. A lock error that survives the retries above queues the write for a daemon thread, which retries it after 30, 60, 120, 240 and 480 s (`DB_DEFERRED_WRITE_RETRY_SECONDS`). Each deferral, each retry that is still blocked and each completion is logged at `WARNING`; a write that fails its last retry, or arrives when `DB_DEFERRED_WRITE_QUEUE_MAX` (200) writes are waiting, is logged at `ERROR` and dropped. An error other than a lock error propagates to the caller. The queue is in memory and is lost on a restart.
* **Short write transactions:** a writer that does slow work per item (a Yahoo call, a Parquet read, a model score) finishes that work before it writes, or commits after each item, so the transaction never spans the slow step. `market_pulse_write.fetch_and_save_pulse()` commits after each ticker, the anomaly backfill commits after each ticker, and the News Feed sentiment pass scores every article before one batched `UPDATE`. A `SQLite write transaction held` warning names a writer that breaks this.
* **Writers that use it:** `db.database.log_notification()` and the in-app channel of `notification_engine.notify()` (the row keeps its original time), `db.helpers.upsert_fx_quote()` when it opens its own connection, the Workflow Monitor run records (`scheduler_engine.record_job_run()` and `_record_job_duration()`), and `PatternDetectionEngine._write_results()`. Writes that the next scan rewrites within minutes (live prices, the account performance cache) are not deferred.
* **A retry must not overwrite newer data:** while a queued write runs, `db.connection.replaying_deferred_write()` is true, and a writer of a value that later writes supersede adds a newer-wins condition in that case only (`market_pulse_cache.fx_updated_at`, `scheduler_run_log.last_run`, `pattern_detection_results.scan_ts`, and a stale-row delete limited to rows older than the scan). A direct write is unconditional.

### Database File Swap Gate (`db/connection.py`)

A backup restore replaces `data/analysis.db` while the web server, the cache-refresh workers and any task already queued keep opening connections. A connection that spans the replacement writes to the old file or pairs a stale `-wal` with the new one, so `get_connection()` counts every connection it hands out (released on `close()`, or when the object is collected) and `db.connection.database_swap_gate()` controls them:

* **Closed gate:** a new `get_connection()` waits up to `DB_SWAP_GATE_WAIT_SECONDS` (60 s), then raises `DatabaseSwapInProgress` (a `sqlite3.OperationalError` with a fixed message).
* **Drain:** with the gate closed, the restore waits up to `DB_SWAP_DRAIN_TIMEOUT_SECONDS` (30 s) for the open connections to close. If any stay open it raises `DatabaseInUse`, the gate reopens and nothing live has changed (`backup_engine` turns this into `RestoreBusy`, answered `409`).
* **Span:** the gate stays closed across the extraction of `data/` and `models/` and the swap of the database, and reopens in a `finally`. The restore's own reads happen before it closes; a connection opened with `sqlite3.connect()` directly is outside the count (only the Backup & Recovery engine does that, on the staged copy and for its snapshot).

A long-lived connection (held open across network work) makes the drain time out, so a connection is opened late and closed early (the connection pattern in `AGENTS.md`).

### Core Tables & Entities

#### `market_universe`
* **Purpose:** The master tracker of all ~4,000+ available equities, ETFs, and Mutual Funds.
* **Key Columns:** `ticker` (PK), `company_name`, `sector`, `industry`, `country`, `exchange`, `is_freetrade`, `freetrade_url`, `last_updated`.

#### `asset_profiles`
* **Purpose:** Static, slow-moving corporate metadata. Stored separately (3NF normalization) to prevent querying Yahoo Finance for static data.
* **Key Columns:** `ticker` (PK), `company_name`, `sector`, `quote_type`, `business_summary`, `last_verified_date`.

#### `profile_empty_strikes`
* **Purpose:** Consecutive empty-answer count per ticker for the Fundamentals Data Profiler. Yahoo's 404 for a symbol it does not know looks the same as a transient miss, so a ticker is blacklisted only on the 5th consecutive empty answer (`profile_engine.EMPTY_ANSWERS_TO_BLACKLIST`); a failed call (429, exhausted 5xx, timeout) neither adds nor clears a strike, and a valid profile deletes the row.
* **Key Columns:** `ticker` (PK), `strikes`, `last_empty_at`.

#### `company_name_overrides`
* **Purpose:** Stores user-defined display name overrides per ticker. When present, the override takes precedence over `asset_profiles.company_name` and `market_universe.company_name` in the portfolio, watchlist, and stock detail pages.
* **Key Columns:** `ticker` (PK), `display_name` (user-supplied name, NOT NULL), `updated_at` (UTC timestamp).
* **Write path:** `POST /api/ticker/{ticker}/name-override`. Sending an empty `display_name` deletes the row (clears override). Read-path is a `LEFT JOIN` in the portfolio, watchlist, and stock detail SQL queries.

#### `stock_signals`
* **Purpose:** The primary aggregation table for the Portfolio & Watchlist UI. It houses the final System Verdicts and Fundamental Health snapshots.
* **Key Columns:** `ticker` (PK), `current_price`, `trend_50d`, `trend_200d`, `atr_stop_loss`, `trailing_pe`, `debt_to_equity`, `peter_lynch_peg`, `yield_correlation`, `composite_score`, `overall_signal`, `setup_tags`.
* **Date columns:** `next_earnings_date` and `ex_dividend_date` are `YYYY-MM-DD` text (`'Unknown'` or NULL when Yahoo reports none), written by the Quant Scan and the Universe Fundamentals sync through `utils.epoch_to_iso_date()` for the ex-dividend date. A `migrate_db()` step converts any stored raw Yahoo epoch (it leaves an epoch at or before 2000-01-01 alone; the next write of that ticker converts it). Read by `db.helpers.get_next_earnings_dates()` / `get_ex_dividend_dates()` (the MCP Server's `get_calendar`) and `reports_engine.get_dividend_harvest_setups()`, which drops a row whose value is not a real `YYYY-MM-DD` date instead of converting it.
* **Forensic Columns:** `piotroski_f_score` (REAL, 0–9 integer stored as real), `altman_z_score` (REAL), `beneish_m_score` (REAL), `forensic_last_updated` (TEXT UTC). Written monthly by the Forensic Accounting Scores job. NULL until first run.
* **ETF/Fund Holdings Columns:** `top_holdings` (TEXT — JSON list of `{"symbol", "name", "weight"}` for a fund's top-10 constituents, from `yahoo_engine.get_fund_holdings()`), `sector_weightings` (TEXT — JSON list of `{"name", "weight"}`, Title Case GICS-style sector names summing to ~1.0, from `yahoo_engine.get_fund_sector_weightings()`), and `holdings_updated_at` (TEXT UTC, freshness marker shared by both — refetched after 30 days). Written for `quote_type IN ('ETF', 'MUTUALFUND')` tickers already held/watchlisted, by `universe_fundamentals_engine.sync_etf_holdings_cache()`, called from `run_update_pipeline` (`quant_analysis_job`, Mon–Fri 18:00 UTC) right after the quant scan. `top_holdings` is consumed by `markets_engine.resolve_benchmark_for_holdings()` — see "ETF Crash-Alert Benchmark Resolution" below — so Crash Alerts can reference the index a fund actually tracks instead of always defaulting to S&P 500, and by `xray_engine._builtin_account_holdings()` to approximate a fund's Geographic Exposure from its top-10 holdings' own countries (rescaled to 100% of the resolvable subset — Yahoo has no direct country-breakdown field for funds). `sector_weightings` is consumed by the same X-ray function to blend a fund's real sector composition into Sector Exposure instead of bucketing it as "Unclassified". NULL for non-fund tickers and for funds not yet processed by that job.
* **`ml_confidence`:** REAL, 0-100 scale — mirrors `quant_signals.ml_confidence_score` (the live source) onto this one-row-per-ticker snapshot, written by `ml_inference_engine.update_daily_ml_predictions()` in the same pass that updates `quant_signals`, and set to NULL for a requested ticker that was not scored and has no `quant_signals.ml_scored_at` inside the freshness window. It exists as a one-row-per-ticker join target for the Regime-Weighted Conviction Score and is kept in sync every time ML inference runs (Mon–Fri, `ml_inference_job`).

#### `quant_signals`
* **Purpose:** Stores a daily historical log of technical and quantitative metrics for machine learning and mean-reversion analysis.
* **Key Columns:** `ticker`, `date` (Composite PK), `close_price`, `rsi_14`, `macd_hist`, `sma_50`, `sma_200`, `volume_surge`, `bullish_cross`, `ml_confidence_score`, `ml_scored_at`, `sentiment_score`, `var_95`, `cvar_95`.
* **ML Score Columns:** `ml_confidence_score` (REAL, 0-100) and `ml_scored_at` (TEXT UTC `YYYY-MM-DD HH:MM:SS`, set with every score by `update_daily_ml_predictions()`). Every reader accepts a score only when `ml_scored_at >= db.helpers.ml_fresh_since()`, which is `constants.ML_FEATURE_MAX_AGE_TRADING_DAYS` trading days back: the readers that carry the latest non-NULL score forward past newer rows (Portfolio/Watchlist rows, Stock Detail, the live ML pillar of Signal Pillar Confluence) and the readers of the latest row's own score (the Dividend Harvest and GARP reports, the AI prompt, the intraday alert metadata, the Market Screener). A new reader of `ml_confidence_score` does the same.
* **Sentiment Score Columns:** `sentiment_score` (REAL, FinBERT mean in [-1, 1] — written by the NLP Market Sentiment Engine, `huggingface_engine.update_all_sentiment()`, onto each ticker's latest-date row; `NULL` when the ticker has no headline inside `SCHEDULING.SENTIMENT_ENGINE.MAX_NEWS_AGE_DAYS`) and `sentiment_scored_at` (TEXT UTC `YYYY-MM-DD HH:MM:SS`, set with every non-NULL score). Readers that carry the latest non-NULL score forward past newer rows only accept one whose `sentiment_scored_at >= db.helpers.sentiment_fresh_since()`. The migration clears `0.0` scores that a retired Yahoo news endpoint caused every scan to store (rows with `sentiment_scored_at IS NULL` only, so a real zero is never touched).
* **Entry & Exit Zone Columns:** `vp_poc` (Volume Profile Point of Control price), `vp_val` (Value Area Low), `vp_vah` (Value Area High), `vp_entry_zone` (nearest HVN or VAL below current price — buy-entry support level), `vp_exit_zone` (nearest overhead HVN or VAH — take-profit resistance level), `kc_z_score` (Keltner Channel Z-score: (Close − EMA21) / ATR14 — negative = below EMA), `kc_entry_signal` (1 if Z-score ∈ (−3, −2) AND 200-day uptrend), `kc_exit_signal` (1 if Z-score > +3 AND RSI > 75).
* **Quantile Price Band Columns:** `price_q10` (10th-percentile 10-day price floor from XGBoost quantile regression), `price_q90` (90th-percentile 10-day price ceiling — optimistic take-profit target). Written by `score_quantile_predictions()` in `ml_inference_engine.py` during the daily ML inference job, together with `quantile_scored_at` (TEXT UTC `YYYY-MM-DD HH:MM:SS`), which is separate from `ml_scored_at` because the classifier and the quantile models are scored by separate writers. Every reader accepts a band only when `quantile_scored_at >= db.helpers.ml_fresh_since()`: Portfolio/Watchlist rows and Stock Detail read the latest row's band, and `db.helpers.get_latest_quantile_bands()` (Predicted Movers, Stable Shortlist, the position-sizing risk/reward gate, the Earnings Volatility page) carries the latest fresh band forward past a newer row that has none. An unstamped or older band shows as unavailable.
* **AI Interaction:** The ML inference engine (`ml_inference_engine`) reads the newest complete row of every ticker (after the universe indicator refresh writes it), keeps the rows inside the freshness window, calculates ML probabilities, and writes `ml_confidence_score`, `ml_scored_at`, `price_q10`, `price_q90` and `quantile_scored_at` back into it daily.

#### `quant_scan_states`
* **Purpose:** Composite-key state tracker for resumability in long-running jobs to prevent data gaps upon unexpected interruptions. On startup, `resume_interrupted_scans()` queries this table and re-fires any IN_PROGRESS scan automatically.
* **Key Columns:** `scan_date`, `scan_type` (Composite PK), `last_processed_ticker`, `status`.
* **`scan_type` values:**
  - `'daily'` — overnight portfolio+watchlist quant scan (`quant_engine.py`)
  - `'universe'` — weekend full-universe quant scan (`quant_engine.py`)
  - `'universe_deep_sync'` — Stage 3 technicals within the deep sync pipeline (`quant_engine.py`)
  - `'ml_backfill'` — ML historical feature backfill per ticker (`ml_backfill_engine.py`); date-agnostic lookup so cross-day restarts still resume
  - `'deep_sync_s1'` … `'deep_sync_s5'` — per-stage checkpoints for the Universe Deep Sync pipeline (`universe_deep_sync_engine.py`); Stage 3 uses `'universe_deep_sync'` above

#### `earnings_volatility`
* **Purpose:** The options arbitrage ledger, plus signed post-earnings drift stats for the long-term-investor framing of `/earnings-volatility`. One row per tracked ticker with earnings in the next 14 days; `implied_move_pct`/`edge_score`/`options_volume` are NULL when the ticker has no liquid ATM options quote (the row is still written as long as drift stats were computable).
* **Key Columns:** `ticker` (PK), `next_earnings_date`, `implied_move_pct` (isolated straddle move, NULL if no liquid quote), `historical_avg_move_pct` (unsigned 1-day), `edge_score` (NULL if no liquid quote), `options_volume` (NULL if no liquid quote), `drift_avg_pct_1d`/`drift_up_count_1d`/`drift_sample_size_1d`, `drift_avg_pct_5d`/`drift_up_count_5d`/`drift_sample_size_5d`, `drift_avg_pct_20d`/`drift_up_count_20d`/`drift_sample_size_20d` (signed average % change, count of positive events, and sample size out of the last 4 earnings events, at each horizon).
* **Written by:** `earnings_vol_engine.run_earnings_vol_scan()`, called by the `weekend_earnings_vol_scan_job` scheduler job.

#### `earnings_volatility_history`
* **Purpose:** Per-scan-day snapshot of `edge_score`/`drift_avg_pct_5d` for a ticker, retained (unlike `earnings_volatility`, which is latest-only) so the Statistical pillar of Signal Pillar Confluence can look back over a rolling window of scans. Only populated while a ticker is within `run_earnings_vol_scan()`'s ~14-day pre-earnings window, so rows are sparse outside that window by design.
* **Key Columns:** `ticker`, `scan_date`, `edge_score`, `drift_avg_pct_5d` — `UNIQUE(ticker, scan_date)`.
* **Written by:** `earnings_vol_engine.run_earnings_vol_scan()`, alongside `earnings_volatility` in the same scan.

### System, Macro & AI Models Tables

#### `market_regimes`
* **Purpose:** Tracks broad market volatility regimes, the HMM surface state, and the market-wide Isolation Forest stress score.
* **Key Columns:** `date` (PK), `vix_close`, `spy_volatility`, `us_turbulence`, `us_regime_label`, `uk_turbulence`, `uk_regime_label`, `ai_hmm_state`, `price_hmm_state` (0=Bull/1=Chop/2=Crash), `price_hmm_label` (text label), `price_hmm_prob` (posterior probability of current state), `market_stress_score` (REAL [0,1] — 1.0 = maximally anomalous), `market_stress_features` (TEXT — JSON blob of the 6 raw feature values: `vix_level`, `vix_ma_ratio`, `hyg_return`, `tnx_change`, `spy_vol_zscore`, `spy_return`).

#### `price_hmm_states`
* **Purpose:** Full Viterbi-decoded state history from the price-action HMM — one row per trading day. Used by the `/market-regime` page and the `/api/market-regime` endpoint.
* **Key Columns:** `date` (PK), `state` (INTEGER 0/1/2), `label` (TEXT: Bull/Chop/Crash), `probability` (REAL posterior confidence).

#### `macro_regimes`
* **Purpose:** Dual-region tracker for systemic threat levels derived from sovereign bond yields and exchange rates. Also stores the synthesised macro regime label computed by `regime_engine.classify_macro_regime()`. `tyx_close`, `dxy_close`, `gbpusd_close` and the UK trio (`uk_gilt_close`, `uk_yield_velocity`, `uk_threat_level`) are `NULL` when the fetch or the gilt baseline was unavailable; the writer never stores `0.0` or a `^TNX` substitute, and a rerun on the same date keeps an earlier good value (`COALESCE` upsert).
* **Key Columns:** `date` (PK), `tyx_close`, `tnx_close`, `dxy_close`, `uk_gilt_close`, `gbpusd_close`, `us_yield_velocity`, `us_threat_level`, `uk_yield_velocity`, `uk_threat_level`, `yield_curve_inverted` (0/1), `days_inverted` (consecutive day streak), `regime_label` (one of: Risk-On, Late Cycle, Stagflation, Contraction, Recovery).

#### `macro_calendar`
* **Purpose:** Tracks Tier-1 economic events, their ground-truth effects on the SPY, and AI-predicted volatility warnings.
* **Key Columns:** `event_id` (PK), `event_date`, `event_name`, `forecast_val`, `previous_val`, `actual_val`, `post_event_spy_gap`, `ai_volatility_warning`, `ai_consensus_miss_prob`, `forecast_text`, `previous_text`, `actual_text`.
* **Numbers and vote splits:** `forecast_val`, `previous_val` and `actual_val` are `REAL`; a feed value that is a central-bank vote split (`7-0-2`) is not a number, so the writer stores it as written in the matching `*_text` column and leaves the number `NULL`. Exactly one of a field's two columns is set when the feed gave a value. `db.helpers.macro_event_value(event, field)` returns the number, else the text, and every display reader (Market Sentiment page, AI prompts, MCP `get_calendar`) uses the `*_text` columns for display only; the Macro AI Engine reads the `REAL` columns and never sees a split. `actual_text`, like `actual_val`, keeps its stored value when a later feed run omits it.
* **Upcoming events have one reader:** `db.helpers.get_upcoming_macro_events(start, end)` returns the rows in a UTC window plus the newest stored date. The MCP Server's `get_calendar`, the AI prompt's 7-day Tier-1 radar (`ai_engine`, High impact only, 12 rows) and the Market Sentiment page (urgent 48 h, US and UK lists, from one 7-day read) and the Market Sentiment prompts (`ai_sentiment_engine`: per currency, highest `ai_consensus_miss_prob` first with NULL last, at most 5) all call it and filter by impact or currency in Python. The feed behind the Macroeconomic Automation Schedulers (Calendar) job lists the current week only, so the table rarely holds events further ahead; `ai_volatility_warning` defaults to `0.0` and is meaningful only where `ai_consensus_miss_prob` is not NULL.

#### `macro_indicators`
* **Purpose:** A structural economic datastore integrating FRED, BoE, and ONS metrics (M2 Supply, Jobless Claims, Yield Curve, CPI, Fed Funds Rate, real yield, nominal GDP growth).
* **Key Columns:** `date` (PK), `us_m2`, `us_jobless_claims`, `us_high_yield_spread`, `us_yield_curve`, `uk_m4`, `uk_corporate_spread`, `us_cpi_inflation`, `us_fed_funds_rate` (FEDFUNDS), `us_real_yield_10y` (DFII10 TIPS), `uk_base_rate` (IUDBEDR), `us_nominal_gdp_yoy` (FRED `GDP`) and `uk_nominal_gdp_yoy` (ONS `YBHA`) — nominal GDP year-on-year %, quarterly data forward-filled onto the daily rows from each quarter's release date (US: quarter end + 30 days, UK: quarter end + 45 days). Read through `macro_data_engine.get_nominal_gdp_yoy_series(region)` for the Yield vs Nominal GDP chart and warning-box line (see `assets/systematic_risk.md`); display-only, no ML consumer.

#### `treasury_auction_results`
* **Purpose:** US Treasury auction demand metrics fetched from the free fiscaldata.treasury.gov API. One row per CUSIP × auction date. Powers the Sovereign Debt Auction Monitor, which fires an alert when bid-to-cover or yield tail is significantly below/above the 6-auction rolling baseline for that maturity. Only auctions with published results are stored; announced-but-not-yet-held auctions are skipped. Each run upserts every resulted auction since the newest stored one (minus a 3-day overlap, at most 180 days back), so a missed run self-heals and rows are filled in rather than left as placeholders. `migrate_db()` clears the table once if it holds rows with NULL results, and the next run rebuilds it from the API.
* **Key Columns:** `cusip` + `auction_date` (composite PK), `maturity_label` (e.g. "10Y", "30Y", "4W"; a reopening pools with its original term via `original_security_term`, bills keep their own term, and TIPS/FRN auctions are separate series such as "10Y TIPS" and "2Y FRN"), `high_yield`, `bid_to_cover`, `tail_bp` (high_yield − median_yield in basis points; for bills the highest − average discount rate, NULL for FRNs, which report no yield), `direct_pct`, `indirect_pct`, `dealer_pct`, `offering_amt` (raw API value), `alert_fired` (0/1 weak flag, re-derived for every stored row on each run from the current rule: bid-to-cover more than 0.2 below / tail more than 2 bp above the 6-auction baseline of the same `maturity_label`, widened to 0.4 / 4 bp for bills, FRN and TIPS; only a newly weak auction dated today notifies). Engine: `treasury_auction_engine.py`.

## 2. Local File Storage (`data/` Directory)

We offload heavy time-series math and unstructured payload caching to local file storage.

* 📁 **`data/historical/` (`.parquet`)**: 2 years of daily OHLCV data. Used by `ta` to calculate moving averages and by `plotly` to render interactive charts.
* 📁 **`data/intraday/` (`.parquet`)**: 1 day of 5-minute interval OHLCV data. Used by the `intraday_orchestrator` to detect flash crashes.
* 📁 **`data/fundamentals/` (`.json`)**: Raw, unadulterated `.info` dictionary dump directly from Yahoo Finance.
* 📁 **`data/fundamentals/quarterly/` (`.json`)**: Annual financial statement cache used by the Forensic Screener. One JSON file per ticker (`{TICKER}.json`) containing `balance_sheet`, `financials`, and `cashflow` DataFrames serialised to dict. Incremental — files younger than 30 days are skipped on re-fetch. Exempt from maintenance pruning (the maintenance engine only processes files directly in `data/fundamentals/`, not subdirectories).
* 📁 **`data/backtest_history/` (`.parquet`)**: Optional ~5-year daily history for the tickers a Strategy Backtester user prepared (and the benchmark), written through `daily_history_writer.prepare_daily_history()`. Separate from `data/historical/`: the nightly refresh and maintenance pruning never touch it and it is never merged into the 2-year cache.
* 📁 **`data/strategy_backtests/<run_id>/` (`.parquet`)**: Per-run equity, allocation and transaction series for the Strategy Backtester (`equity.parquet`, `allocations.parquet`, `transactions.parquet`). Deleted with the run row. Both folders are inside `data/`, so Backup & Recovery includes them.
* 📄 **`data/portfolio.json`**: Contains positions, shares, and VWAP synced from Ghostfolio (both Macro and Micro ledgers). Only exists while `GHOSTFOLIO_ENABLED` is `true` — unchecking **Enable Ghostfolio Integration** in Settings deletes it immediately, and the nightly maintenance job / System Configuration Check re-delete it if it reappears (e.g. restored from a backup) while disabled. `accounts.accounts_engine._read_portfolio_json()` also short-circuits to `{}` when the flag is off, regardless of whether the file exists.
* 📄 **`data/watchlist.json`**: Legacy active-watchlist file, superseded by the `watchlist_items` table (see §1) — only read once at startup for the one-time migration. Same disabled-Ghostfolio deletion lifecycle as `portfolio.json` above.
* 📄 **`data/freetrade_blacklist.json`**: Self-healing ledger of permanently banned tickers. The Fundamentals Data Profiler adds a ticker only after 5 consecutive empty Yahoo answers (`profile_empty_strikes`). Entries are removed manually from Settings → Core System & Currencies → Freetrade Blacklist (`POST /api/universe/blacklist/remove`).
* 📄 **`data/isin_ticker_cache.json`**: Mapping of European ISINs to Yahoo Finance symbols.
* 📄 **`data/exchange_hours.json`**: Per-exchange open/close times, timezones, currencies, and ticker suffixes. Auto-seeded with defaults for 28 exchanges on first boot; on every subsequent `init_db()` run, `db.schema._seed_exchange_hours_json()` also backfills any exchange or field in `_DEFAULT_EXCHANGE_HOURS` that this install's file lacks (e.g. LSE's `quote_delay_minutes`), without overwriting any field already present — so an install seeded before a default field existed self-heals on the next restart. Edit this file to customise or add exchange definitions; read at runtime by `time_engine.py` and `etf_predictor_engine.py`.

## 3. The AI & Machine Learning Architecture

The dashboard features a tri-level AI architecture that interacts heavily with both the SQLite and Local File Storage layers.

### A. The LLM Prompt Aggregator (`AIPromptEngine`)
Located in `ai_engine.py`, this engine acts as a massive data bridge. It extracts data across the Dual-Storage architecture to generate high-context, institutional-grade prompts for external LLMs.
1. **SQLite Extraction:** Joins `stock_signals` and `quant_signals` to pull the latest system verdicts, ML Confidence Scores, VaR/CVaR, and NLP Sentiment.
2. **JSON Extraction:** Pulls live global VWAP, active shares, and unrealized P&L from `portfolio.json`.
3. **Parquet Extraction:** Reads raw `.parquet` historical files on-the-fly to calculate real-time technicals (MACD lines, OBV trends, volume averages).
4. **Prompt Wrapping:** Compiles this cross-storage data into specific personas (e.g., "The Devil's Advocate", "Risk/Reward Audit", "Earnings Strategy").

### B. Micro-Equities Prediction (`AIPredictionEngine`)
An XGBoost + Random Forest soft-voting ensemble that evaluates individual stock momentum.
* **Flow:** Reads 24 features from historical Parquet files and fundamental tables -> Applies cross-sectional z-scoring -> Predicts probability of >3% return in 10 days -> Upserts the `ml_confidence_score` into `quant_signals`.

### C. Macroeconomic Event Prediction (`MacroAIEngine`)
A stacked model architecture that evaluates systemic market risk.
* **Flow:** * **HMM (Hidden Markov Model):** Reads structural `macro_indicators` to predict the hidden regime state (`ai_hmm_state` in `market_regimes`).
  * **Random Forest:** Reads `macro_calendar` forecasts to predict the probability of Wall Street being wrong (`ai_consensus_miss_prob`).
  * **XGBoost (Stacking):** Consumes the HMM state and RF probability to predict the exact percentage shock an upcoming event will have on the S&P 500 (`ai_volatility_warning`).
* **Persistence:** all three models are persisted to `models/macro_hmm.joblib` (bundles the fitted `GaussianHMM`, its `StandardScaler`, and the canonical state-order remap), `models/macro_rf.joblib`, and `models/macro_xgb.joblib` on successful training, and loaded back in `MacroAIEngine.__init__`. Persisting them lets `POST /macro/run-pipeline` (which constructs a fresh `MacroAIEngine`) run inference against trained models without `/macro/init-pipeline` having trained them in the same process; an untrained model logs `"XGBoost Volatility model is untrained. Bypassing stacked inference."`.

## 4. Additional SQLite Tables

Tables added after initial schema creation. All managed via `db/schema.py:init_db()` and `db/schema.py:migrate_db()` (re-exported from `db/database.py`).

#### `ticker_metadata`
* **Purpose:** Lightweight beta + market-cap cache used by ML feature assembly. Created by `ml_backfill_engine.sync_ticker_metadata()` rather than `init_db()` (see code note).
* **Key Columns:** `ticker` (PK), `sector`, `beta`, `market_cap`.

#### `market_pulse_cache`
* **Purpose:** Shared, timestamped live-price cache — the single place any engine that derives a fresh ticker price from a Yahoo Finance fetch shares it, so other engines/pages reuse it instead of re-fetching. It holds the index/asset snapshot behind `/market-sentiment` JS polling and is also written by the Crash & Moonshot scan (`intraday_orchestrator.py`) and Dip Radar (`intraday_bottom_engine.py`) from OHLCV data they already pull for their own pattern detection. Read by `market_pulse.get_cached_pulse_from_db()` (JS polling, with a `needs_refresh` staleness check that skips a fetch once another engine has updated a ticker) and, for the ticking price widget on the Portfolio and Stock Detail pages, `market_pulse.get_all_cached_pulse()`. The Portfolio page's per-position value/P&L math (`page_data_portfolio.finalize_portfolio_rows`), the Stock Detail page's "Your Position" math (`page_data_stock_panels.position_targets`), and Built-in Accounts (`accounts.accounts_engine.current_price_map()` — Accounts holdings table, `portfolio-totals`/`list-with-metrics`/`holdings-list`) all resolve their current price through the single canonical `accounts.accounts_engine.current_price_map()` instead of each reading `market_pulse_cache`/`stock_signals` independently, so a position's value and P&L agree across all three pages for the same request. The JSON list/metrics endpoints and the `/portfolio` page itself self-trigger a `fetch_and_save_pulse()` background task via the shared `api.routes_accounts.maybe_trigger_price_refresh()` for any held ticker whose row is older than `UI_PREFERENCES.REFRESH_RATE`, so loading/polling any of them — a browser tab or Home Assistant — is itself what keeps the cache warm, not just a passive read. `IntradayOrchestrator._run()` localizes its `CRASH_ALERTS.START_TIME`/`END_TIME` (entered as `USER_TIMEZONE` wall-clock, matching the `CronTrigger(timezone=user_tz)` that fires the job) before comparing them with the current time; comparing them with UTC would delay the first successful scan of the day by the DST offset.. `current_price_map()` prefers this cache's price over `stock_signals.current_price` unless the cache row is missing, or has fallen more than `accounts.accounts_engine._STOCK_SIGNALS_OVERRIDE_MIN_GAP_SECONDS` (6h) behind `stock_signals.last_updated` — not a bare "whichever timestamp is newer" comparison, and not gated by an absolute-age cutoff on the cache side either — `market_pulse.is_price_fresh()`'s age-based check (a 5-minute floor, or 2x `REFRESH_RATE` if larger) is display-only, feeding the "grey out as stale" flag on the live-ticking widget, not data selection. The minimum gap exists because Crash & Moonshot stops refreshing this cache for the day at its own local-time `CRASH_ALERTS.END_TIME`, but the nightly Update Pipeline writes a fresh `stock_signals.last_updated` ~1-2h later: a bare "newer wins" comparison would flip to the nightly price for that gap every night even when the cache still held the day's real close. A stale nightly price (`utils.is_daily_bar_still_forming()` gets an exchange-open signal through `data_engine._drop_in_progress_last_bar()` so a same-day post-close fetch is not mistaken for a mid-session one) could then win the race and get baked into `account_performance_cache.return_1d` by the still-running `account_performance_refresh_job`, producing a visible jump in account values right as the nightly pipeline ran. The gap is the defense-in-depth half; `account_performance_refresh_job`'s schedule window is also limited (see that table's entry below) to reduce the exposure window itself. The Crash & Moonshot scan's write into this table (and its own Crash/Moonshot/Anomaly/HoldingLimit evaluation of the same price) is gated per-ticker on `market_session_helpers.is_quote_settled(exchange)`: ungated, a held LSE ticker scanned within Yahoo's ~15-minute post-open feed lag could push a stale/delayed quote into this shared cache (and fire a false Crash/Moonshot/Anomaly alert off it), the same race `accounts.accounts_engine.tickers_needing_refresh()` guards against — see `assets/anomaly_detection.md` §8. The "prefer live unless stuck more than 6h behind `stock_signals`" protection also covers the ticking price widget and daily change % shown by `get_all_cached_pulse()`/`get_cached_pulse_from_db()`: without it, a row that stopped being refreshed (a ticker newly bought into a built-in account before its first live tick, or any ticker background jobs stopped keeping warm) could display an arbitrarily old, wrong price on the Portfolio/Watchlist page indefinitely, even while the same page's P&L figure (computed via `current_price_map()`) had self-corrected from `stock_signals`. The gap check lives in `db.helpers.resolve_live_price()` (with `parse_utc_epoch()`), shared by `current_price_map()`, `get_all_cached_pulse()` and `get_cached_pulse_from_db()` so three readings of the same two tables cannot disagree — see AGENTS.md rule 16. When the fallback wins, `change_pts`/`change_pct` are cleared to `None` rather than left paired with a price they no longer describe.
* **Key Columns:** `ticker` (PK), `name`, `price`, `change_pts`, `change_pct`, `is_positive`, `last_updated`, `market_state`, `extended_price`, `extended_change_pts`, `extended_change_pct`, `extended_session`. `market_state` holds the live Yahoo `marketState` value (`"REGULAR"`, `"CLOSED"`, `"PRE"`, `"POST"`, ...) for the 8 exchange-status proxy tickers in `market_session_helpers.MARKET_STATUS_PROXY` (`^GSPC` NYSE, `^FTSE` LSE, `^GDAXI` XETRA, `^N225` TSE, `^HSI` HKEX, `000001.SS` SSE, `^AXJO` ASX, `^FCHI` Euronext) — `market_session_helpers.is_exchange_open(exchange)` reads it to give `GET /api/system/market-status`/`GET /api/system/market-status/all` and `accounts.accounts_engine.tickers_needing_refresh()` an open/closed check — holiday-vetoed first via `time_engine.is_exchange_holiday()` (backed by `exchange_calendars`, the one canonical holiday source for all 29 registry exchanges, not just these 8), then this cached `market_state` for the 8 proxied exchanges, falling back to `time_engine.is_trading_session()`'s weekday/hours heuristic (itself holiday-vetoed, and sourcing the day's actual open/close, including early closes/half-days, from `exchange_calendars` via `time_engine.market_window_utc()` rather than the static `exchange_hours.json` entry alone) for any exchange without a proxy, or when no live state is cached yet. `GET /api/system/market-status`/`market-status/all` self-trigger a `fetch_and_save_pulse()` background task for any proxy ticker whose `market_state` is missing or older than 5 minutes (`market_pulse.proxy_tickers_needing_refresh()`), so a caller that only ever polls those endpoints (e.g. Home Assistant, never opening a browser dashboard) still keeps `market_state` warm instead of it going stale forever. `market_state` is written for *every* fetched ticker (not just the 8 proxies) as a side effect of the single `.info` fetch `get_quote_snapshot()` does for every ticker.

  **`extended_price`/`extended_change_pts`/`extended_change_pct`/`extended_session`** keep pre-market/after-hours data out of `price`/`change_pts`/`change_pct`, which must never mix regular-session closing data with extended-hours ticks (a mixed price would show the Portfolio/Stock Detail pages and, transitively, `accounts.accounts_engine.current_price_map()`/`accounts/portfolio_metrics_engine.py`'s Home Assistant endpoints a confusing, non-representative price with no way to tell it apart from a real close). `yahoo_engine.get_quote_snapshot(ticker)` (one cached `.info` call, 5 min TTL) is the primary source in `fetch_and_save_pulse()`: `price`/`change_pts`/`change_pct` are always Yahoo's own `regularMarketPrice`/`regularMarketChange`/`regularMarketChangePercent` — the real closing/regular price, never an extended-hours tick, by construction. The two change fields are Yahoo's own only while they agree with its price and `regularMarketPreviousClose` within `constants.QUOTE_CHANGE_TOLERANCE_PCT` percentage points; when they contradict the same payload (a change equal to the negative of the previous close, a percent of about -50), `market_session_helpers.regular_change_from_snapshot()` derives both from the price and the previous close and logs a warning, and the 50% plausibility guard still skips a consistent move that large. Extended fields: `extended_price`/`extended_change_pts`/`extended_change_pct` are populated **only** when Yahoo's own `marketState` says `"PRE"`/`"PREPRE"` or `"POST"`/`"POSTPOST"` is genuinely active and Yahoo actually returned the corresponding `preMarketPrice`/`postMarketPrice` field, with `extended_session` set to `"pre"`/`"post"` accordingly — cleared to `NULL` otherwise, even if Yahoo's payload carries a stale extended-hours field forward into a `"CLOSED"`/`"REGULAR"` state. Session is never inferred from wall-clock time — only from Yahoo's own `marketState`. The daily/intraday diffing logic (`utils.is_daily_bar_still_forming()`) is a self-healing fallback used only when `get_quote_snapshot()` itself is unavailable (Yahoo error/rate-limit), in which case `extended_*` stays `NULL` rather than being guessed. Because `accounts.accounts_engine.current_price_map()` and `accounts.portfolio_metrics_engine._market_pulse_change_map()` only ever read the plain `price`/`change_pts`/`change_pct` columns, every P&L/total/Home-Assistant consumer is pure by construction. The extended fields are read-only display data: the Portfolio page's "Show After Market Data" toggle (`portfolio_show_extended` cookie) shows them in brackets under the Price column only when enabled; the Stock Detail page always shows a Pre-Market/After Hours line when present, with no toggle.

  **Fallback branch gate.** When `get_quote_snapshot()` returns `None` and the ticker has a live intraday feed (ordinary equity/ETF, not a daily-only mutual fund), `fetch_and_save_pulse()` falls back to that feed's last bar (fetched with `prepost=True`) as "the price" only if `market_session_helpers.is_exchange_open(exchange)` confirms the exchange is in regular session, so the last bar is genuinely a regular-session tick. Otherwise a transient Yahoo `.info` failure during an actual pre/post session would write a pre/post tick straight into `price`/`change_pts`/`change_pct`, bypassing the `extended_*` separation. When the gate is closed, the ticker's price/change columns are left untouched for that cycle (a no-op, not a write of stale/wrong data) and the next scheduled/triggered call retries `get_quote_snapshot()` — no blocking retry-with-backoff loop is needed, since `_maybe_alert_stale_ticker()` (same loop, per AGENTS.md rule 10) surfaces a ticker that stays stuck failing through its own trading session. The mini-sparkline write (a separate concern — it's meant to show today's full session including extended hours) runs from the same live feed regardless of this gate. For FX, futures and rates with a stored `instrument_sessions` row, this gate and the in-progress-daily-bar check use Yahoo's reported window (`time_engine.reported_window_open()` / `reported_bar_still_forming()`) instead of an exchange.
* **Written by:** `market_pulse_write.upsert_live_price()` (shared writer, name preserved via `COALESCE` if already on record) or `market_pulse_write.fetch_and_save_pulse()`'s own insert (index/mutual-fund/gilt fallback paths). The latter also fires a once-per-day `stale_price_alert` notification (via `alert_state` dedup, engine `stale_price`) when a held ticker's fetch has been failing for 30+ minutes during its own market hours.
* **Retention:** the weekly **Database & File Maintenance** job (`maintenance_engine.prune_pulse_cache()`) deletes a row only if it is **both** older than 24h **and** orphaned — not currently tracked by any writer (`maintenance_engine._get_pulse_active_tickers()`: portfolio holdings, watchlist, `market_pulse.get_index_tickers()` — sourced from `market_ticker_registry`, see below — `"UK10YG"`, `ai_contagion_engine.AI_ECOSYSTEM_TICKERS`, active Dip Radar monitors). A currently-held ticker's row therefore survives indefinitely across a weekend/holiday market closure instead of being wiped by the weekly prune before the next session can refresh it (a blind 24h-age prune would wipe every held ticker's row every weekend). Separately, `accounts.accounts_engine.tickers_needing_refresh()`'s market-hours gate (only auto-refresh while a market is open, to avoid pointless Yahoo calls when nothing can have changed) has a bootstrap exception: a ticker with **no** cached row at all is still refreshed even while both markets are closed, since a genuinely missing row — a fresh install, a newly-bought ticker, or a gap — could otherwise never self-heal until a market reopened. An already-cached ticker is additionally gated on `market_session_helpers.is_quote_settled(exchange)`, not just `is_exchange_open()` — Yahoo's free LSE feed runs ~15-20 minutes behind the real market (see `quote_delay_minutes` in `exchange_hours.json`), so without this gate the instant LSE opens, the first Home Assistant/portfolio-page poll would trigger `fetch_and_save_pulse()` to pull a not-yet-representative delayed quote into this table, which would change on every subsequent poll as Yahoo's feed caught up — a visibly wrong, self-correcting blip in every account gain figure derived from it right at market open. `intraday_bottom_engine.run_scan()` (Dip Radar) gates its own armed-ticker scan the same way. This per-ticker exchange resolution + settlement check is a single shared helper, `market_session_helpers.is_ticker_quote_settled()` (backed by `market_session_helpers.resolve_ticker_exchange()`/`build_registry_exchange_map()`), rather than each caller reimplementing it — `accounts.accounts_engine.tickers_needing_refresh()` calls it, and the same helper backs `market_pulse.get_cached_pulse_from_db()`'s per-tile `needs_refresh` and `market_pulse.registry_tickers_needing_refresh()` (see `assets/markets_page.md` §10), so the Markets page/Market Pulse's refresh gating is exchange-aware per ticker.

#### `market_ticker_registry`
* **Purpose:** Single source of truth for every index/commodity/FX ticker tracked by the Markets page (`/markets`) and Market Pulse (there is no hardcoded ticker dict in `market_pulse`). Read via `market_pulse.get_index_tickers()` (every enabled row — name lookups, "is this one of our own tracked instruments" classification) and `market_pulse.get_pulse_index_tickers()` (only `is_pulse_tile=1` rows, ordered by `pulse_sort_order` — the static Market Pulse tile set). `markets_engine.py` reads it directly (via `db.database.get_ticker_registry()`) for region grouping, dynamic ordering, and spot/future resolution. Editable from Settings → Markets & Market Pulse (`/api/markets/registry` CRUD) — a write immediately busts `market_pulse`'s in-process cache via `reload_ticker_registry()`, no restart needed.
* **Key Columns:** `ticker` (PK, spot/primary Yahoo symbol), `display_name`, `region` (`Europe`|`US`|`Asia`|`Commodities_FX`), `asset_type` (`Index`|`Commodity`|`FX`|`Rate`|`Volatility`), `exchange` (key into `time_engine.EXCHANGE_HOURS`; `NULL` = always-visible, no session gating — used for `Commodities_FX` rows since none of gold/silver/copper/oil/DXY/EUR-GBP-USD pairs map cleanly to one exchange; the `UK10YG` rate row is the exception and carries `LSE`, so its refresh gate does not follow `HOME_EXCHANGE`), `currency`, `future_ticker`/`future_display_name` (paired front-month future for the 5 dual-instrument indexes — S&P 500, Nasdaq 100, Dow, Russell 2000, Nikkei 225; `NULL` for everything else), `invert_color` (1 = rising value is risk-off — yields, DXY, oil), `is_pulse_tile`/`pulse_sort_order`/`is_pulse_mobile` (static Market Pulse membership/order/mobile-visibility), `sort_order` (tie-break order within a Markets-page region section), `enabled` (soft-delete), `context_blurb`/`baseline_parquet` (feed the `/index/{ticker}` detail page).
* **Ticker format:** writers refuse a ticker that fails `utils.is_valid_ticker()` (1-64 characters from `A-Za-z0-9^.=_-`, case kept) — the stored value becomes a file name in the per-ticker engines, which also build every path through `utils.safe_ticker_filename()`.
* **Seed data:** 25 rows inserted via `INSERT OR IGNORE` in `db.schema._seed_market_ticker_registry()` on every `init_db()` run — idempotent, never overwrites a row already edited via Settings (`migrate_db()` additionally fills a `NULL` `UK10YG` exchange with `LSE` on an existing database). The 10 default Market Pulse tickers are seeded with `is_pulse_tile=1`, so a fresh install shows that static tile set until the operator edits the registry or enables `UI_PREFERENCES.MARKET_PULSE_DYNAMIC`.
* **Nightly fetch universe:** every enabled row's `ticker` and `future_ticker` are unioned into `data_engine.DataEngine.get_all_tickers()` alongside Portfolio/Watchlist/Accounts, so the nightly Update Pipeline downloads 2Y daily history and `QuantEngine.run_all()` populates `quant_signals` technicals for every Markets page ticker without a manual per-ticker refresh. See `assets/markets_page.md` §9.

#### `market_pulse_sparkline`
* **Purpose:** Today's-session intraday points feeding the Markets page's per-tile mini chart (a lightweight inline SVG polyline, not a Plotly instance — see `assets/markets_page.md`). Written by `market_pulse_write.fetch_and_save_pulse()`: on each fetch cycle with fresh intraday data, the ticker's existing rows are deleted and the fresh series, thinned by `market_pulse_write._thin_points()` to at most 60 evenly spaced points that always include the first and the newest bar, is inserted — a full replace, not an append, since the sparkline is inherently "today's session." When a ticker's intraday fetch returns empty (market closed), the write step is skipped entirely for that ticker, so the last session's points persist — this is what produces a flat/last-known line instead of a blank tile when a market is shut. `UK10YG` (FT.com snapshot, no intraday feed) is the exception: `_append_gilt_sparkline()` appends each live FT reading, drops rows from before the current UTC day and thins with the same `_thin_points()`; a Parquet-fallback value is never appended.
* **Key Columns:** `ticker`, `ts` (unix timestamp of the intraday bar; for `UK10YG`, of the FT reading), `price` — composite PK `(ticker, ts)`.
* **Read by:** `market_pulse.get_intraday_points(ticker, max_points=60)`, called from `markets_engine.assemble_markets_payload()` per tile.

#### `instrument_sessions`
* **Purpose:** The exchange timezone and regular-window end Yahoo reports for instruments that no `exchange_calendars` calendar models — FX pairs, futures (including the registry's `future_ticker` rows), `^`-prefixed rates/indexes without a registry exchange, and registry rows with `exchange = NULL`. Yahoo buckets their daily bars on that window (FX: the London calendar day; futures and DXY: the New York day; `^TNX`/`^TYX`: the CBOE window 07:20-14:00 Chicago), so `daily_history_writer.prepare_daily_history()` trims a bar dated today in that timezone until the window has ended, and `daily_history_cache_revision()` treats a file written before the latest window end as stale. A ticker with no stored row is judged by the exchange session exactly as before (plain tickers as NYSE).
* **Key Columns:** `ticker` (PK), `exchange_tz` (IANA name from Yahoo's `exchangeTimezoneName`), `regular_end` (`HH:MM` local time of the end of Yahoo's `currentTradingPeriod.regular` window), `updated_at` (UTC).
* **Written by:** `daily_history_writer._learn_reported_session()`, called from `prepare_daily_history()` on the refresh that first needs a ticker's session and again after 30 days; the lookup is `yahoo_engine.get_session_shape()` (chart metadata, one request per candidate ticker, retried at most hourly after a failure). A failed refresh keeps the last stored row. `UK10YG` (an FT/BoE series) is excluded from Yahoo fetches by `utils.is_excluded_from_yahoo_fetch()` and never gets a row.
* **Read by:** `market_session_helpers.reported_session()` (process-wide in-memory copy of this table, loaded on first use): `daily_history_writer.prepare_daily_history()` and `daily_history_cache_revision()` for the daily bar, `market_session_helpers.is_ticker_quote_settled()` for refresh gating, and `market_pulse_write._quote_from_live_feed()` for the fallback quote's session and prev-close check. `daily_history_writer._learn_reported_session()` writes a newly learned session into the same in-memory copy.

#### `alert_state`
* **Purpose:** Dedup ledger for intraday alert engines. Decoupled from `system_notifications` so display and dedup logic never interfere. Daily ML Inference keeps one row per Portfolio/Watchlist ticker it has warned about (engine `ml_inference_stale_features`), deleted when the ticker is scored again.
* **Key Columns:** `engine`, `ticker` (composite PK), `fingerprint`, `last_price`, `last_fired_utc`, `armed`, `fire_count`, `state_date`.
* **`state_date` and pruning:** `IntradayOrchestrator._prune_alert_state()` deletes rows whose `state_date` is more than 7 days old (`intraday_orchestrator.py`, docstring: "only delisted/removed tickers accumulate"). `_evaluate_alert_gate()` bumps `state_date` to today on every suppressed path (the "can't compare" fallback and Case 4c), via the shared `_touch_alert_state_date()` helper. Without the bump, a genuinely still-active, correctly-suppressed condition (unchanged fingerprint, no material worsening) that never needed to fire for more than 7 days would have its row pruned, and the next scan would see "no prior state" (Case 1) and fire a byte-identical alert as if brand new. This mirrors the orphan-aware prune of `market_pulse_cache` (`maintenance_engine.prune_pulse_cache()`): a row that keeps getting checked never goes stale enough to be pruned, while a row nothing ever scans again (a genuinely delisted/removed ticker) still ages out normally.

#### `system_notifications`
* **Purpose:** In-app notification feed surfaced in the Settings notifications panel.
* **Key Columns:** `id` (PK autoincrement), `timestamp`, `message_type`, `message_text`, `is_read`, `status`.
* **Written by:** all notifications funnel through `notification_engine.notify()`, whose in-app channel writes this table (directly, or via `db.database.log_notification()`). A write that loses the SQLite lock is retried later with its original time (see Write-Lock Handling). Whether a given source reaches this table is controlled by `NOTIFICATION_ROUTING`. Deep pipeline-progress messages still call `db.database.log_notification()` directly (in-app only).
* **Read by the MCP Server:** `get_alerts` reads the alert rows through `db.helpers.get_recent_alert_notifications(since, limit)`, which returns only rows whose `message_type` is in `notification_engine.ALERT_MESSAGE_TYPES` (the `alert_type` of each `NOTIFICATION_SOURCES` entry). Job-status types (Info, Success, Scheduler, Warning, Error, Maintenance) and any unregistered type are never returned, because their text can carry raw exception text.
* **Auto-read types:** rows with `message_type` in `Info`/`Success`/`Scheduler` (`database.AUTO_READ_MESSAGE_TYPES`) are inserted with `is_read = 1` — these don't need operator triage, so they never contribute to the unread badge or the `/notifications` page's "unread" card highlight.
* **Page-level filtering (client-side only):** the `/notifications` page's type filter buttons (`static/js/notifications.js`) are multi-select — clicking more than one (e.g. Crash and Moonshot) shows the union of both — plus an independent "Unread Only" toggle ANDed against the type selection. Both are pure DOM filters over the server-rendered/polled cards (no new query params on `GET /api/notifications/latest`) and persist across reloads via `localStorage` (`notif_active_types`, `notif_unread_only`).

#### `nextcloud_talk_stats`
* **Purpose:** One row per UTC day counting the Nextcloud Talk text messages the app sent and the ones that failed, for the Nextcloud Talk row of Settings → System Diagnostics. Counters restart each day because each day is its own row.
* **Key Columns:** `stat_date` (PK, TEXT UTC `YYYY-MM-DD`), `sent` and `failed` (INTEGER counters), `last_success_utc` and `last_failure_utc` (TEXT UTC `YYYY-MM-DD HH:MM:SS`, NULL until the first one), `last_error` (TEXT, the last failure as `HTTP <status>` or the exception class; never a URL, token or message text).
* **Writes:** `nextcloud_talk.send_text_message()` through `db.helpers.record_nextcloud_talk_attempt()` after every real send (a call with no Talk configuration is not an attempt); a failed stats write is logged and never changes the send result.
* **Reads:** `db.helpers.get_nextcloud_talk_today()` for `GET /api/system/metrics`. The state is `failing` when `last_failure_utc` is not older than `last_success_utc`, `ok` when the last send worked, `idle` with no row for today.
* **Retention:** 90 days (`NEXTCLOUD_TALK_STATS_RETENTION_DAYS`); `MaintenanceEngine.prune_nextcloud_talk_stats()` runs in the weekly Database & File Maintenance job.

#### `scheduler_run_log`
* **Purpose:** Records the latest run timestamp and aggregate timing per APScheduler job ID so jobs can guard against re-running within their minimum interval and the Workflow Monitor can report current health.
* **Key Columns:** `job_id` (PK), `last_run`, `last_started`, `last_duration_sec`, `avg_duration_sec` (plain mean of the job's last 20 successful runs in `scheduler_run_history`; failed runs are excluded, and a job with no successful run keeps its previous value), `last_status` (`success`/`error`).
* **Written by:** each job's `record_job_run()` (`last_run`) plus the shared scheduler execution wrapper (`last_started`, duration, status) used by scheduled and Settings **Run Now** paths. `db.helpers.refresh_job_average_duration()` recomputes `avg_duration_sec` after every run and once per `migrate_db()`; the Workflow Monitor and the Settings **Active processes** list both read this one value. #### `trap_phase_history`
* **Purpose:** Append-only log of trap phase assignments per ticker per day, used to evaluate prediction accuracy retroactively and as the training set for the Alert Confidence Referee (see below). One row per (ticker, scan_date) — the first scan of each day is kept.
* **Key Columns:** `id` (PK autoincrement), `ticker`, `phase`, `scan_date` (YYYY-MM-DD), `scan_ts` (UTC ISO), `close_price` (reference price at scan time), `rsi` / `ema_distance` / `bull_trap_vol_ratio` / `cap_vol_zscore` / `wyckoff_bb_width` (the same signal features captured on `trap_monitor_results` at scan time, so a historical row carries the features that drove the phase call, not just the call itself — rows without them have these columns NULL until backfilled, see `alert_referee_engine.backfill_historical_features()` below), `actual_price_14d` / `actual_date_14d` / `direction_correct_14d` (filled ~14 calendar days later), `actual_price_30d` / `actual_date_30d` / `direction_correct_30d` (filled ~30 calendar days later), `pillar_technical` / `pillar_statistical` / `pillar_ml` (`up`/`down`/NULL — Buy-Signal Confluence Pipeline Part A's per-pillar vote at scan time), `regime_weighted_score` (Part B's 0-100 score at scan time, or NULL for "no signal"), `confluence_features_ts` (UTC ISO — when the four columns above were computed; NULL means not yet computed, distinct from a pillar genuinely abstaining, which is also NULL).
* **Constraint:** `UNIQUE(ticker, scan_date)` — `INSERT OR IGNORE` keeps the first result of each day.
* **Written by:** `bull_bear_trap_engine.TrapEngine._save_results()` → `db.database.log_trap_phase()` (which returns `True`/`False` reporting whether a new row was actually inserted, used by `scheduler_jobs.run_trap_monitor_job()` to gate the Cross-Engine Alert Referee's shadow evaluation to once per ticker per day). Actuals filled daily by `trap_accuracy_fill_job` via `bull_bear_trap_engine.fill_trap_phase_actuals()`.

Before every training run, `alert_referee_engine.backfill_historical_features()` recomputes the feature columns above for any `trap_phase_history` row still missing them (`ema_distance IS NULL AND phase != 'NEUTRAL'`), reloading that ticker's 2-year parquet and re-running the same detector pipeline (`bull_bear_trap_engine.TrapEngine._analyse_ticker()`) as of that row's `scan_date` — so rows logged without the feature columns become usable training data immediately if already resolved, rather than only new scans contributing. A row is only updated if the recomputed phase matches the originally-recorded phase (a mismatch means the parquet has since been revised, so the recomputed features would no longer describe the outcome that was actually recorded); idempotent, since already-backfilled rows are excluded from the candidate query. The `pillar_*`/`regime_weighted_score`/`confluence_features_ts` columns have their own equivalent backfill, `alert_referee_engine.backfill_historical_confluence_features()` — see `pattern_detection_history` below and `assets/buy_signal_confluence_pipeline.md` Part C.

#### `alert_referee_models`
* **Purpose:** One row per Alert Confidence Referee training run — a small `RandomForestClassifier` (isotonic-calibrated via `CalibratedClassifierCV`, mirroring `ml_training_engine.py`'s calibration approach). Two engines: `TrapMonitor` (trained on `trap_phase_history`'s resolved, feature-bearing rows) and `Confluence` (the Cross-Engine Alert Referee, Buy-Signal Confluence Pipeline Part C — trained on the pillar-vote/regime-score columns unioned across `trap_phase_history` and `pattern_detection_history`). Each engine has its own joblib artifact and its own `SCHEDULING.ALERT_REFEREE_TRAINING*` config block, so the two never share readiness/Shadow-Active state.
* **Key Columns:** `id` (PK autoincrement), `engine` (`TrapMonitor` | `Confluence`), `trained_at` (UTC ISO), `sample_count`, `positive_count` (rows where the resolved outcome label is 1), `train_accuracy`, `veto_rate` (fraction of the training set the model would veto at the configured threshold), `effective_mode` (`shadow` | `active` — the mode this training run actually qualified for, given `sample_count` vs. the configured `MIN_TRAINING_SAMPLES`), `model_path` (joblib artifact path — `models/alert_referee_trapmonitor.joblib` or `models/alert_referee_confluence.joblib`).
* **Written by:** `alert_referee_engine.train_referee_model(engine)`, called from the `alert_referee_training_job`/`confluence_referee_training_job` scheduler jobs or the Settings "Run Training Now" action (`POST /api/alert-referee/train?engine=...`).

#### `alert_referee_log`
* **Purpose:** Per-evaluation shadow/active log — every time either referee engine is consulted, its verdict is recorded here, whether or not the veto was actually enforced. This is what lets an operator see "what would the referee have done" while it runs in Shadow mode.
* **Key Columns:** `id` (PK autoincrement), `engine` (`TrapMonitor` | `Confluence`), `ticker`, `phase` (the Trap Monitor phase label — NULL for `Confluence` rows), `direction` (the Confluence engine's bullish/bearish call — NULL for `TrapMonitor` rows; a dedicated column rather than overloading `phase`, since the two concepts differ per engine), `fire_probability` (the calibrated model's confidence the signal is a genuine hit), `vetoed` (0/1 — whether the model recommended a veto, regardless of mode), `mode` (`shadow` | `active` — the effective mode at evaluation time), `model_id` (the `alert_referee_models.id` used, no enforced FK), `scan_ts` (UTC ISO).
* **Written by:** `alert_referee_engine.log_veto_evaluation()`, called from `alert_referee_engine.evaluate_alert()` on every Trap Monitor phase call the referee is consulted on, and — since the Cross-Engine Alert Referee shipped — on every ticker whose confluence direction is (re)computed on the first `trap_monitor_job` scan of the day (see `pattern_detection_history` below for why `pattern_detection_job`'s own scan doesn't independently trigger a second evaluation).
* **Index:** `idx_alert_referee_log_engine_ticker` on `(engine, ticker)`.
* **Read by:** `alert_referee_engine.get_recent_evaluations()` (optional `since_ts` lower bound on `scan_ts`) — the Settings log, `GET /api/alert-referee/log` and the MCP Server's `get_alerts`.

#### `pattern_detection_results`
* **Purpose:** Latest Pattern Detection scan result per ticker **per pattern family** — one row per `(ticker, pattern_family)` pair, upserted on each scan, so a ticker can carry a confirmed Double Top and a forming Head & Shoulders simultaneously without either overwriting the other. Powers `/pattern-detection` live table. Head & Shoulders results live in this generic table (see Migration note below); the `head_shoulders_results` table is kept in the schema as an inert artifact and is never written to.
* **Key Columns:** `id` (PK autoincrement), `ticker`, `pattern_family` (`head_shoulders` | `double_top_bottom` | `flag` | `pennant` | `triangle` | `wedge` | `volatility_squeeze` | `narrow_range` | `parabolic_stretch` | `momentum_divergence` | `candlestick_trigger`, extensible), `pattern_type` (family-specific variant, e.g. `regular`/`inverse`, `double_top`/`double_bottom`, `bull_flag`/`bear_flag`, `bull_pennant`/`bear_pennant`, `ascending`/`descending`/`symmetrical_triangle`/`symmetrical_triangle_bullish`/`symmetrical_triangle_bearish`, `rising_wedge`/`falling_wedge`, `volatility_squeeze`/`volatility_squeeze_bullish`/`volatility_squeeze_bearish`, `nr4`/`nr7`/`nr4_bullish`/`nr4_bearish`/`nr7_bullish`/`nr7_bearish`, `parabolic_stretch_overbought`/`parabolic_stretch_oversold`, `bearish_divergence`/`bullish_divergence`, or `bullish_engulfing`/`bearish_engulfing`/`hammer`/`shooting_star`), `phase` (`FORMING` | `CONFIRMED` — `candlestick_trigger` rows are always `CONFIRMED`, since a 1-2 bar trigger has no forming state), `points_json` (JSON array of `{label, date, price}` — the pattern's labeled structural pivots, geometry-agnostic across families), `lines_json` (JSON array of `{label, date_from, price_from, date_to, price_to, dash}`, or `{label, path: [{date, price}, ...], dash}` for a genuine curve rather than a straight segment — neckline/support/resistance/trendline/band-contour segments), `breakout_date`/`breakout_price` (NULL until confirmed), `measured_target` (the classic technical-analysis price objective, family-specific formula), `volume_confirms`/`rsi_divergence` (0/1 supporting signals), `pattern_r2` (fit quality of the pattern's piecewise-linear model vs. actual price — NULL for a family with no such fit, e.g. Volatility Squeeze/Narrow Range/Parabolic Stretch), `prior_trend_pct` (the required prior directional move before the pattern's first structural point), `scan_ts`.
* **Constraint:** `UNIQUE(ticker, pattern_family)`.
* **Written by:** `pattern_detection_engine.PatternDetectionEngine._save_results()`. New families register in `pattern_detection_engine.DETECTORS` — see `assets/pattern_detection.md`.

#### `pattern_detection_history`
* **Purpose:** Append-only log of every detected pattern per ticker per day (across every pattern family), used to evaluate prediction accuracy and populated retroactively by a one-time historical backtest (`pattern_detection_engine.backfill_historical_patterns()`, triggered via Settings → "Backfill Historical Data" or `POST /api/pattern-detection/backfill`) that walks each ticker's full 2-year parquet at ~weekly intervals per family and resolves outcomes immediately, since for historical dates the future is already in the parquet — unlike `trap_phase_history`, which only accumulates forward.
* **Key Columns:** `id` (PK autoincrement), `ticker`, `pattern_family`, `pattern_type`, `phase`, `scan_date` (YYYY-MM-DD), `scan_ts` (UTC ISO), `close_price`, `measured_target`, `volume_confirms`, `rsi_divergence`, `pattern_r2`, `prior_trend_pct`, `actual_price_14d`/`actual_date_14d`/`direction_correct_14d`, `actual_price_30d`/`actual_date_30d`/`direction_correct_30d`, `pillar_technical`/`pillar_statistical`/`pillar_ml`/`regime_weighted_score`/`confluence_features_ts` (same meaning as the equivalent `trap_phase_history` columns above — populated by `PatternDetectionEngine._save_results()` for every row it logs, feeding the Cross-Engine Alert Referee's training set; see `assets/buy_signal_confluence_pipeline.md` Part C).
* **Constraint:** `UNIQUE(ticker, scan_date, pattern_family, pattern_type)` — a ticker can independently log candidates from every enabled pattern type, across every family, on the same day.
* **Written by:** `pattern_detection_engine.PatternDetectionEngine._save_results()` → `db.database.log_pattern_detection()`. Actuals filled daily by `pattern_detection_accuracy_fill_job` via `pattern_detection_engine.fill_pattern_outcomes()`. Only `CONFIRMED` phase rows are ever resolved — a `FORMING` candidate hasn't made a directional prediction yet. Rows logged before the Cross-Engine Alert Referee shipped (or via `backfill_historical_patterns()`, which doesn't compute these columns at insert time) get them recomputed as-of their own `scan_date` by `alert_referee_engine.backfill_historical_confluence_features()` before every Confluence training run — no engine re-run needed, since pillar votes/regime are themselves just windowed reads over other tables (`score_analysis.evaluate_pillar_confluence_as_of()`/`compute_regime_weighted_score_as_of()`), unlike `trap_phase_history`'s own RSI/EMA backfill which does need to re-run `TrapEngine._analyse_ticker()` against parquet.
* **Migration note:** `db.schema.migrate_db()` copies any existing `head_shoulders_results`/`head_shoulders_history` rows into these generic tables (`pattern_family='head_shoulders'`, the five named pivot columns reshaped into `points_json`, the neckline into a single `lines_json` entry) exactly once, idempotently, the first time this migration runs against a database that holds them.

#### `pairs_spread_results`
* **Purpose:** Latest Pairs Spread Monitor scan result — one row per correlated same-currency pair, per scope (`portfolio_watchlist` or `universe`). Fully replaced per scope (not upserted) on every scan of that scope, so a pair that drops out of the correlation threshold disappears rather than lingering with a stale `scan_ts`, and a Universe scan never clears Portfolio+Watchlist rows or vice versa. Powers `/pairs-spread`.
* **Key Columns:** `pair_key` (PK, `"{scope}:{ticker_a}:{ticker_b}"` — scope-prefixed so the same pair can independently appear in both scopes without a PK collision), `scope`, `ticker_a`, `ticker_b`, `currency` (normalized — GBp/GBP collapse to `GBP`), `correlation` (Pearson, trailing 252-day daily returns), `zscore` (log-spread deviation from its own trailing-year mean), `spread_mean`, `spread_std`, `last_spread`, `direction` (human-readable "X rich vs Y" string), `cheap_ticker`/`rich_ticker` (the same information as `direction`, split into two columns so a consumer can read a pair's cheap side as a value without string-parsing), `scan_ts`. Company names are not stored here — joined at read time from `stock_signals.company_name` via `db.helpers.get_company_names()`.
* **Written by:** `pairs_spread_engine.PairsSpreadEngine.run_scan(scope=...)` → `PairsSpreadEngine._save_results()`, called by the `pairs_spread_monitor_job` scheduler job (`portfolio_watchlist` scope only) and by `scheduler_jobs.run_pairs_spread_universe_scan()` (`universe` scope, on-demand only — not a scheduled job). The underlying log-spread/price time series itself is never persisted — `pairs_spread_engine.build_chart_series()` recomputes it on demand from `data/historical/*.parquet` for the chart endpoint.

#### `sector_relative_momentum_results`
* **Purpose:** Latest and recent Sector-Relative Momentum standing per ticker and window — each stock's cumulative return over the last `window_sessions` trading sessions versus the leave-one-out median return of its sector x currency peers. Scored rows are stored for the whole peer pool; unavailable-reason rows are stored only for Portfolio/Watchlist tickers. Powers `/sector-relative-momentum`, the four optional Portfolio/Watchlist columns and the AI prompt's sector comparison.
* **Key Columns:** `ticker`, `window_sessions` (63 or 126), `as_of_date` (the cohort's last completed session), `status` (`ok`, or the reason a ticker could not be scored: `no_metadata`, `not_equity`, `no_sector`, `no_currency`, `no_history`, `insufficient_history`, `small_cohort`), `sector`, `currency` (normalized — GBp/GBP collapse to `GBP`), `window_start_date`, `cohort_size` (scored members including the ticker), `peer_count` (members excluding the ticker), `own_return` and `peer_return` (fractions, `0.12` = 12%), `relative_return_pp` (percentage points: `100 x (own_return - peer_return)`), `rank` (1 = strongest, ties broken by ticker), `percentile` (0-100, higher = stronger, ties share an average rank), `input_revision` (short digest of the window's scored inputs), `computed_at` (UTC). Return and rank columns are NULL when `status != 'ok'`.
* **Constraint:** `PRIMARY KEY (ticker, window_sessions, as_of_date)` — a same-day rerun replaces rows (`INSERT OR REPLACE`); readers take the latest `as_of_date` per ticker and window.
* **Retention:** after each run, rows whose `computed_at` is more than 30 days before that run's `computed_at` are deleted. Keyed to `computed_at`, not `as_of_date`: a cohort whose parquet is stale has an `as_of_date` weeks behind the newest, and its rows must still persist.
* **Written by:** `sector_relative_momentum_engine.run_sector_relative_momentum()`, called by `scheduler_jobs.run_sector_relative_momentum_job()` (`sector_relative_momentum_job`). Never written by a page request.

#### `predicted_movers_history`

#### `yahoo_api_stats`
* **Purpose:** Daily aggregated counters for all `yahoo_connection_boundary` invocations. Used by the Yahoo Finance API Usage card in Settings to show request volume, interface breakdown, rate-limit hits, errors, and yfinance-logged issues over the past 8 days.
* **Key Columns:** `date` (PK TEXT `YYYY-MM-DD` UTC), `total_calls`, `ipv4_calls`, `ipv6_calls`, `rate_limit_429`, `other_errors`, `yfinance_logged_errors` (all INTEGER, default 0).
* **Writes:** Appended via a background daemon queue in `tools/network_engine._increment_api_stat()`. The queue drains to `_write_api_stat()` which uses SQLite `ON CONFLICT DO UPDATE` (upsert) so concurrent writes never corrupt the counters.
* **Reads:** `db.database.get_yahoo_api_stats(days=8)` → `GET /api/system/yahoo-api-stats`.
* **`yfinance_logged_errors` note:** `other_errors` only counts calls where an exception actually propagated out of `yahoo_connection_boundary` — but the `yfinance` library frequently logs its own ERROR-level line (e.g. "possibly delisted; no price data found", a 404 on a quoteSummary module Yahoo doesn't support for that instrument) and just returns an empty/partial result instead of raising, so those would be invisible to this table despite flooding the Log Viewer. `tools/network_engine._YfErrorNoiseFilter` (a `logging.Filter` attached to `logging.getLogger("yfinance")`) counts ERROR-level records into a thread-local counter for the duration of each `yahoo_connection_boundary` call (safe under concurrent/interleaved boundaries — see the lock-scope note below — because the counter is `threading.local()`, so each thread's tally is independent regardless of how many boundaries are simultaneously live); the count is read in the boundary's `finally` block and threaded through as a 4th argument to `_increment_api_stat()`. The same filter also demotes the specific "possibly delisted" line to DEBUG (so it stops reaching `app.log`/Log Viewer at the default INFO file-logging level) whenever `tools/network_engine.suppress_yf_delisted_noise(True)` is active on the calling thread — counting always happens first, so demotion never hides the event from this table, only from the human-facing log.
* **Lock scope / session reuse:** `yahoo_engine._yf_singleton_lock` wraps every yfinance call site's session-negotiate-plus-fetch — required because yfinance's `YfData` is a hard process-wide singleton that would otherwise race on its shared `_session`/`_crumb`/`_cookie` state (see `yahoo_engine.py`'s module comment). Two things limit how much wall-clock time it costs: (1) `yahoo_connection_boundary` reuses one curl_cffi `Session` per interface (`tools/network_engine._session_cache`, keyed `"ipv4"`/`f"ipv6:{addr}"`) instead of building a fresh one — and paying its TLS/Chrome-impersonation handshake — on every call; the IPv6-only failover branch (`create_failover_session`) is deliberately excluded, since its `fallback_triggered`/rebuild logic assumes a fresh session per call. (2) A retryable network error (a timeout, a connection reset, an HTTP 5xx) never sleeps under the lock: `_patch_session_with_retries` only records it on the session (`_transient_failures`) and re-raises, because it runs on yfinance's own worker threads (`yf.download` uses a thread pool over one shared session), which cannot release a lock their caller holds. `yahoo_connection_boundary(raise_on_transient=True)` turns a recorded failure into `_TransientNetworkError`, including one yfinance swallowed, and `yahoo_engine._yahoo_call` (which every call site uses, replacing the `with _yf_singleton_lock:` / boundary pair) releases the lock, sleeps `network_engine.transient_backoff_seconds(attempt)` and reruns the whole call, up to `TRANSIENT_MAX_RETRIES` times; the last attempt does not ask for the raise and returns or raises whatever yfinance produced. Work that a waiting caller's cache re-check must see (the intraday cache write) runs inside the callable, under the lock. The ISIN search has no yfinance singleton to protect and runs with `locked=False`. The IPv6-only failover session (`create_failover_session`) keeps its own in-wrapper retry with `_sleep_outside_lock`, because its retries decide when the IPv6 fault latch trips (AGENTS.md rule 10). The HTTP 429 handler (`_enter_yahoo_rate_limit`) clears the cached crumb through `_clear_yfinance_crumb()`, which takes `YfData._cookie_lock` without waiting and leaves the crumb as it is when the lock is held: yfinance holds that non-reentrant lock while it fetches the crumb, so a 429 on the crumb request itself reaches the handler on the thread that already owns it, and waiting would hang that thread and every Yahoo caller behind `_yf_singleton_lock`. While the 429 cooldown is open the patched sessions (`_patch_session_with_retries` and `create_failover_session`) raise the rate-limit error for a request that has not been sent (`_raise_if_rate_limited`), so `yf.download` workers still running when one of them is rate-limited stop adding 429s to a limited IP; `yahoo_rate_limit_trips()` counts the breaker trips.
* **Yahoo 5xx handling:** Yahoo's `quoteSummary` endpoint returns an occasional transient 500 (for example during the always-on HA market-registry refresh, `api.routes_accounts._refresh_markets_registry()`); yfinance itself swallows this exception internally and returns `None`, so it would log a bare `HTTP Error 500: {...}` line with no `job_id`/`action_context` and never reach our own `except Exception:` blocks where `action_context` is known. `_patch_session_with_retries()` and `create_failover_session()` treat any `response.status_code >= 500` the same as a transient network exception. For the cached session the retry is `_yahoo_call`'s, logged as "Transient network error during '%s'" with the call's own `action_context` (so it never reads `'unknown'`). If the last attempt still fails, the wrapper raises `tools.network_engine._TransientHTTPError` (message includes `action_context`) *before* the response ever reaches yfinance's own parsing, so it propagates to the caller's `except Exception: logger.error(...)` instead of being logged bare — and `yahoo_connection_boundary` correctly records it as `status="error"` (not `yfinance_logged_errors`, since yfinance's own logger never sees it).

* **Yahoo intraday data-gap tracking (in-memory, central to `yahoo_engine.py`):** `YahooEngine.get_intraday()` drops all-NaN-`Close` rows from each ticker's slice of a bulk download (a multi-ticker download is on the union of every ticker's bar times; an all-NaN slice is returned empty and still counts as an answer, not a gap) and wraps its primary fetch with `suppress_yf_delisted_noise(True)`/`(False)`, because an empty intraday result for a correctly-profiled ETF/stock is a known false-positive class for "possibly delisted" (an ETF such as LCJP.L/SMGB.L can have full daily-bar coverage and a live quote while Yahoo's `period=1d` intraday endpoint has zero prints for it that session). The gap is not papered over with a wider `period`, which would silently substitute stale multi-day-old data for what callers expect to be near-live bars; instead the engine tracks each empty ticker's gap start time in `YahooEngine._intraday_gap_since` (in-memory dict, resets on restart — acceptable since a real gap re-detects and re-times itself within `_INTRADAY_GAP_ALERT_MINUTES` regardless) and clears it the moment a fetch for that ticker succeeds again. Once a ticker has been empty continuously for `_INTRADAY_GAP_ALERT_MINUTES` (30 min), `YahooEngine._notify_intraday_gap()` fires **one** aggregated `yahoo_intraday_gap_alert` notification covering every ticker that crossed the threshold in that call — not one per ticker and not one per caller, since Crash/Moonshot, Dip Radar, and the ETF Predictor all call `get_intraday()` and would otherwise each fire their own alert for the same underlying Yahoo-side gap. A matching recovery notification fires once when a previously-alerted ticker's fetch succeeds again. `YahooEngine.is_intraday_gap_alerted(ticker)` is the read-side accessor: `GET /api/intraday-chart/{ticker}` and `POST /api/intraday-chart/refresh` (`api.routes._intraday_gap_notice_html()`) use it to prepend a `.box-warning` notice to the Stock Detail intraday chart HTML instead of silently rendering a possibly-stale cached chart with no indication it isn't live.

* **Yahoo daily-history data-gap tracking (in-memory, `yahoo_engine.py`):** mirrors the intraday tracker immediately above, but for `YahooEngine.get_price_history()` — it catches a ticker silently falling out of the nightly `bulk_download_historical()` call (a handful of names can be dropped from a single ~4,000-ticker `yf.download()` even though Yahoo returns fresh data when queried directly), which would otherwise leave that ticker's daily parquet stale with no retry and no alerting. `YahooEngine._history_gap_since`/`_history_gap_alerted` track each empty ticker the same way `_intraday_gap_since`/`_intraday_gap_alerted` do; once a ticker has returned no daily history continuously for `_HISTORY_GAP_ALERT_MINUTES` (1800 min / 30h — daily bars only refresh ~once/night, so this means "missed a nightly run", not a transient blip), `YahooEngine._notify_history_gap()` fires one aggregated `yahoo_history_gap_alert` notification, with a matching recovery notification once the fetch succeeds again. This tracker only detects and alerts — it does not retry or backfill; a stuck ticker still needs its next successful nightly fetch (or a manual "Run Update Pipeline Now") to actually recover. The Update Pipeline's universe step (`bulk_download_historical(..., universe=...)`) goes through the same `get_price_history()` call, so a delisted `stock_signals` ticker is reported once, in the aggregated notification, after it has been empty for two consecutive nightly runs.

Retained 8 days (matching `yahoo_api_stats`'s window) and pruned automatically.

stored only, with no display built on it), `opening_balance_units` (Pension-only in the UI — how many fund units the Opening Balance amount represents; `accounts.accounts_engine.sync_pension_opening_balance()` materialises this + `initial_cash` as a real `Buy` transaction against the synthetic ticker on every create/update, so a pre-existing balance shows real units/holdings immediately rather than starting at zero — see `opening_balance_txn_id`), `opening_balance_txn_id` (FK-ish to `account_transactions.id` — tracks which transaction represents the synced opening balance, so a later edit updates it in place instead of duplicating it, and clearing either field deletes it; #### `account_transactions`
* **Purpose:** Full transaction ledger for built-in accounts. Every activity is retained — including Buys/Sells for tickers no longer held — so closed positions and realized P&L can be derived.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `txn_type` (`Buy` | `Sell` | `Fee` | `Dividend` | `Interest` | `Cash` | `Transfer`), `ticker`, `isin` (optional — International Securities Identification Number, the instrument's permanent identifier independent of ticker symbol changes; manually editable in the Add/Edit Transaction modal next to Ticker, and auto-populated by CSV import when the source file provides it), `company_name`, `currency` (trade currency — USD/EUR/GBP/GBp/…), `txn_date` (YYYY-MM-DD), `quantity`, `unit_price`, `fee`, `exchange_rate` (trade currency → base), `fee_currency` (the currency the `fee` itself is billed in — independent of `currency`, e.g. a broker's FX spread fee already quoted in base currency on a foreign-currency trade; `NULL` defaults to `currency` at read time), `fee_exchange_rate` (fee currency → base; `NULL` defaults to the row's own `exchange_rate` at read time — see `accounts.accounts_engine._fee_fx()`), `notes`, `update_cash` (0/1 — whether the row adjusts the cash balance; always 1 for manually-entered transactions, and the UI has no toggle for it — it stays 0 only for Ghostfolio-imported rows, which have no real deposit history to derive cash from), `price_in_pence` (0/1 — GBp pence), `ghostfolio_ref` (dedup key for imported activities, also reused with a `csv:` prefix by CSV import), `linked_txn_id` (the sibling row's `id` for `Transfer` rows — each transfer is two linked rows, a negative leg on the source account and a positive leg on the destination; `NULL` for every other type), `is_adjustment` (0/1, default 0 — set only by `accounts.accounts_engine.reconcile_cash()` on the synthetic `Cash` row it books to true up drift against a real broker statement; shown as an **Adjustment** badge and filterable in the Activities table; not part of `_ALLOWED_TXN_COLUMNS`, so editing the row's other fields later never clears it), `created_at`.
* **Notes:** `db.account_store.add_transaction()`/`update_transaction()` refuse (log, return `None`/`False`) a `txn_date` that is not a real `YYYY-MM-DD` date, a `currency`/`fee_currency` that is not three ASCII letters (`utils.is_iso_date()`/`is_currency_code()`; `GBp` passes) or a non-empty `ticker` that fails `utils.is_valid_ticker()` (1-64 characters from `A-Za-z0-9^.=_-`, case kept, so a lowercase Ghostfolio asset UUID passes; the same pattern `utils.safe_ticker_filename()` applies to every file name built from a ticker), so every writer — API, CSV import, Transfer, Auto Top-up, Pension, Treasury Bill — is covered. Cost basis is computed in base currency via `exchange_rate`. Holdings, cash, and realized P&L are derived on read by `accounts/accounts_engine.py` — no aggregated snapshot is stored here. `Transfer` rows reuse the `Cash` type's sign convention (negative=outgoing, positive=incoming) so `_cash_delta` needs no special-cased branch. Transfers are created via `accounts.accounts_engine.create_transfer()` (both rows inserted atomically) and deleted via `delete_transaction_with_pair()` (deleting either leg deletes both); they cannot be edited in place — delete and recreate instead. `_cash_delta` converts `fee` using `_fee_fx()` (the fee's own rate) rather than the trade's `_fx()` — not the trade's `exchange_rate`, which would mis-convert a fee billed in a different currency than the trade (e.g. an FX spread fee already quoted in GBP on a USD trade being multiplied by the USD rate a second time).
* **Index:** `idx_account_transactions_account_date` on `(account_id, txn_date)` — serves `db.account_store.get_transactions()`'s `WHERE account_id = ? ORDER BY txn_date, id` (called from ~20 sites, including every account-detail page render and the nightly value-history backfill), which would otherwise be a full table scan + filesort.

#### `account_value_history`
* **Purpose:** Per-day snapshot of each built-in account's value, used to draw the account-value-over-time chart on the account detail page, and as the baseline history for `accounts.accounts_engine.period_returns()`'s 1D/1W/1M/3M/6M/1Y figures. Written nightly by the scheduled job (`account_value_snapshot_job`, `SCHEDULING.ACCOUNT_VALUE_SNAPSHOT.TIME`, default `01:30` — deliberately *after* `overnight_quant_scan_job`'s default `01:00` run finishes writing the verified daily close to `stock_signals`; scheduling the snapshot earlier (e.g. `23:30`) would bake in whatever pre-close price `market_pulse_cache` last had from that day's Crash/Moonshot scan instead of the real close, corrupting every period-return baseline anchored on that night), but also recomputed immediately (via `accounts.accounts_engine.resnapshot_account()`) after every transaction add/edit/delete, transfer, or Ghostfolio import, so the chart never waits a full day to reflect a change. `snapshot_all_accounts()` isolates each account in its own try/except so one account's pricing failure (e.g. a delisted ticker) can't abort the snapshot for every account processed after it that night; an all-or-nothing loop would leave later accounts with a stale baseline (silently wrong period returns) until a manual "Account Value Snapshot" re-run.

    `snapshot_all_accounts(scheduled: bool = True)`: the real nightly job (`scheduled=True`, the default) labels its row `today - 1`, since the job runs shortly after midnight for the trading day that *just* closed. The Settings "Run Now" trigger (`POST /api/accounts/value-snapshot/trigger`, `api/routes_accounts.py`) instead calls it with `scheduled=False`, labelling the row with today's actual date — that endpoint fires on demand at any time of day, producing a live intraday snapshot rather than a reconstruction of last night's close, so applying the same `today - 1` shift would relabel a still-forming mid-day price as an official prior-day close. Using the `today - 1` label for a Run Now during market hours would overwrite the previous day's snapshot with the current live price and collapse `period_returns()`'s 1-day figure to ~0.

    **The nightly-job timing itself creates a predictable ~90-minute gap every night** between local midnight (when `period_returns()`'s "today" rolls over) and whenever `account_value_snapshot_job` actually completes (`01:30` default, plus run time) — during that window, the row for "yesterday" simply doesn't exist yet, so a snapshot-based 1-day baseline would necessarily be an extra day stale. `accounts.accounts_engine._value_as_of_date()` closes this gap: `period_returns()` detects when a window's `target_date` is more recent than the latest row in `account_value_history` and computes that date's value live (same per-ticker Parquet-Close + ledger-replay approach as `backfill_value_history()`, but for a single on-demand date rather than a bulk range) instead of silently falling back to an older, stale snapshot or giving up and returning `None`.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `snapshot_date` (YYYY-MM-DD), `total_value` (cash + equity), `cash_value`, `equity_value`, `net_contributions` (cumulative `initial_cash` + every `Cash`/`Transfer` movement only — excludes Buy/Sell/Dividend/Interest/Fee, so comparing it against `total_value` shows at a glance whether the account is ahead of or behind what was actually put in) — all in base currency. For Pension accounts, `cash_value` is always written as `0` regardless of `cash_balance()`'s `initial_cash` baseline — a Pension has no real cash sub-ledger, so that baseline would otherwise leak in as a phantom constant offset on every row, decoupling `total_value` from the Pension Value tile's `equity_value`.
* **Constraint:** `UNIQUE(account_id, snapshot_date)` — idempotent upsert via `ON CONFLICT DO UPDATE`.

#### `account_value_history_currency`
* **Purpose:** Per-day, per-currency breakdown of each built-in account's equity value — one row per account/day/currency actually held that day. Extends `account_value_history` (which only stores the day's combined total) so a Home Assistant/portfolio-wide Time-Weighted Return can be computed both "as actually experienced" (today's live FX rate) and "FX-neutral" (isolating the equity-only return from currency movement) — see `accounts.accounts_engine.portfolio_twr_fx()` / `portfolio_twr_ex_fx()`.
* **Key Columns:** `account_id` (FK to accounts), `snapshot_date` (YYYY-MM-DD), `currency`, `equity_value_native` (that currency's equity value in its own currency, e.g. USD), `equity_value_base` (the same value converted to `BASE_CURRENCY` using that day's `fx_rate`), `fx_rate` (currency → BASE_CURRENCY rate in effect on `snapshot_date`).
* **Constraint:** `PRIMARY KEY (account_id, snapshot_date, currency)` — idempotent upsert via `ON CONFLICT DO UPDATE`.
* **Writes:** Populated alongside every `account_value_history` write — `accounts.accounts_engine.snapshot_all_accounts()`, `resnapshot_account()`, `backfill_value_history()`, and `_backfill_house_value_history()` all derive the per-currency breakdown from the same equity-valuation pass via the shared `accounts.accounts_engine._bucket_equity_by_currency()` helper, so the two tables are always written together and stay in sync (summing `equity_value_base` across a date's currency rows reproduces that date's `account_value_history.equity_value`).
* **CRUD:** `db.account_store.upsert_value_snapshot_currency()` / `get_value_history_currency()` (both re-exported from `db/database.py`).

#### `account_performance_cache`
* **Purpose:** One row per `Trading` account holding its last computed live-performance figures — total value, equity value, cash balance, unrealized P&amp;L, realized P&amp;L, dividend/interest income, 1D/1W/1M/3M/6M/1Y period gain/loss in `BASE_CURRENCY`, and since-inception Money-Weighted Rate of Return (Modified Dietz method, %) — powering the live tile rows on the Trading account detail page and the Home Assistant `account_metrics_list()` per-account sensor set. Written by `accounts.accounts_engine.refresh_performance_cache()`, called from three places sharing the one canonical loop `accounts.accounts_engine.refresh_all_trading_performance_caches()`: as a side effect of the Crash/Moonshot scan (`intraday_orchestrator_job`, every `CRASH_ALERTS.INTERVAL_MINUTES`, which already fetches live prices for every held ticker into `market_pulse_cache`), the dedicated, always-on `account_performance_refresh_job` (mon-fri 07:00–20:59 UTC, every 1 minute; DB-only re-derivation from the already-cached prices, no Yahoo Finance calls, so it's safe at that cadence independent of the heavier scan's own interval), and immediately after the nightly `account_value_snapshot_job` (`scheduler_jobs.run_account_value_snapshot()`) writes its new baseline, so period-return figures reflect the new trading day right away rather than staying frozen at the last `account_performance_refresh_job` tick until its 07:00 UTC window reopens — this matters because the Home Assistant integration polls while markets are closed (see `CONF_SKIP_REFRESH_WHEN_MARKETS_CLOSED` in the HA integration's own docs). So the figures are computed server-side and shared by every browser/tab that polls `GET /api/accounts/{id}/live-performance`, rather than each poll re-deriving MWRR/period-returns from the full transaction history. Falls back to computing on the fly (still writing the row) if a request arrives before the next scan has populated it — e.g. a brand-new account. `realized_pnl`/`dividend_income`/`interest_income` are derived from the same `account_summary()` call as the other fields in that refresh, so `account_metrics_list()` can read every field from this one cache row instead of mixing it with a separately-timed live `account_summary()` call. **The 07:00–20:59 UTC window** deliberately stops close to Crash & Moonshot's own local-time `CRASH_ALERTS.END_TIME` cutoff (when `market_pulse_cache` stops being refreshed for the day); a window running ~2h past it would create a dead zone the 22:30 Update Pipeline's `stock_signals` write could land in unnoticed. See the `market_pulse_cache` entry's `current_price_map()` note above and `utils.is_daily_bar_still_forming()`.
* **Key Columns:** `account_id` (PK, FK to accounts), `total_value`, `equity_value`, `cash_balance`, `unrealized_pnl`, `return_1d`, `return_1w`, `return_1m`, `return_3m`, `return_6m`, `return_1y` (all currency amounts, `end value − start value − net contributions during the period` — deliberately not a percentage, since dividing by the period's starting value blows up whenever that baseline is small, e.g. a lookback window older than the account itself falling back to the earliest snapshot near opening; a window is `None` if the nearest `account_value_history` row on-or-before that window's target date is more than `accounts.accounts_engine._MAX_BASELINE_GAP_DAYS` (2 days) stale *and* the target date isn't newer than every row we have — that second condition is `accounts.accounts_engine._value_as_of_date()`'s live-fallback case (see `account_value_history` above), which computes the baseline on demand instead of returning `None`; a genuinely wide gap deeper in existing history (e.g. a missed nightly run weeks ago, with normal rows both before and after it) still surfaces as `None`), `mwrr` (%, the one genuinely rate-based metric here — `None` if the account has no contributions yet), `realized_pnl`, `dividend_income`, `interest_income` (currency amounts, from `account_summary()`), `last_updated` (Unix timestamp), `priced_at_cost_count` (INTEGER: holdings valued at cost basis because no price or FX rate was usable when the row was computed; `NULL` on rows written before the column existed).
* **CRUD:** `db.account_store.upsert_performance_cache()` / `get_performance_cache()` (both re-exported from `db/database.py`).

#### `account_price_history`
* **Purpose:** Raw daily price series for the **Account Price Scraper** feature — a generic URL + CSS-selector price feed for `House`/`Pension` accounts, replicating what Ghostfolio's "manual asset" scraper does (the user's own external cron scripts write a small static HTML page such as `<div id="gf-price">123.45</div>`; this table stores what was extracted from it). One row per account per day. For `House`, the latest row *is* the account's equity value directly (`accounts.accounts_engine._equity_value_for_account`). For `Pension`, the row is the fund's unit price, used to value a synthetic single holding (see `account_transactions` note below) and to auto-resolve the price for "Pay In"/"Admin Fee" actions.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `price_date` (YYYY-MM-DD), `price`, `source` (`scrape` | `csv_import` | `purchase` — distinguishes a scheduled/manual scrape, a pasted historical-CSV backfill, or the House purchase-price row `accounts.accounts_engine.sync_house_purchase_price()` seeds at `opened_date`), `created_at`.
* **Constraint:** `UNIQUE(account_id, price_date)` — idempotent upsert via `ON CONFLICT DO UPDATE`, so re-scraping the same day overwrites rather than duplicates.
* **CRUD:** `db/account_store.py` (re-exported from `db/database.py`): `add_price_history`, `get_price_history`, `get_latest_price`, `get_price_as_of`. Fetch/extract/CSV-parse logic lives in `accounts/account_scraper_engine.py`; the outbound-fetch rules (https only, public addresses unless the host is in the `SCRAPER_ALLOWED_HOSTS` config key, pinned IP, no redirects, 2 MB cap, header allow-list) are listed under the Account Price Scraper heading of `assets/api_reference.md`; the fetch itself is `outbound_fetch_helpers.fetch_body()`, which `news_feed_engine.py` also uses for article bodies (2 redirects, each re-vetted, no allow-list).
* **Pension's synthetic holding:** a Pension account's one holding is represented as ticker `PENSION-{account_id}` in `account_transactions` — never shown in the UI, purely an internal key so the existing average-cost ledger (`_ledger_for_account`) can represent "units of the fund" with no changes to that machinery. "Pay In" creates a `Buy` row (units = amount ÷ that date's price); "Admin Fee" creates a `Sell` row sized from the units-before (from the ledger) minus the units-after the user reads off the provider's portal. Both set `update_cash=False` — the money never passes through the account's cash balance. `accounts.accounts_engine.current_price_map()` resolves this ticker's current price from `account_price_history` instead of `stock_signals`.

#### `account_benchmark_tickers`

* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `ticker`, `display_name`, `sort_order` (display order in both the chart legend and the edit modal), `created_at`.
* **Ticker format:** writers refuse a ticker that fails `utils.is_valid_ticker()` (1-64 characters from `A-Za-z0-9^.=_-`, case kept) — the stored value becomes a file name in the per-ticker engines, which also build every path through `utils.safe_ticker_filename()`.
* **Constraint:** `UNIQUE(account_id, ticker)`.
* **CRUD:** `db.account_store.get_benchmark_tickers()` / `replace_benchmark_tickers()` (both re-exported from `db/database.py`) — `replace_benchmark_tickers()` is a wholesale delete-then-reinsert, since the edit modal always submits the full list rather than a diff.
* **Chart overlay math:** `accounts.accounts_engine.pension_benchmark_overlay(account_id, value_df)` rebases every line — the CPI+target line and every ticker benchmark — to the pension's own value on its first `account_value_history` snapshot date, so all lines share the Pension Value line's own value axis rather than needing a separate % return chart. The CPI+target line compounds `macro_data_engine.get_uk_cpi_yoy_series()` (the same UK CPI YoY% series the Market Sentiment page's "UK Price Stability" chart uses — see `macro_indicators.uk_cpi_inflation` above) plus `accounts.benchmark_cpi_target_pct`, converted to a daily rate; each ticker line rebases `data_engine.load_or_fetch_daily_history(ticker)`'s daily Close series to the same starting value. `visuals.create_pension_value_chart()` renders the result as additional dotted Plotly traces with a legend, shown only when at least one benchmark line is present.

#### `holding_price_limits`
* **Purpose:** Stores an optional low/high price alert limit per (account, ticker) holding — a.k.a. "Position Targets" on the Stock Detail page (a standalone box, independent of the Your Position box), and the Home Assistant integration's Low Limit / High Limit number entities. Both surfaces read/write the same rows, so a target set in one place shows up in the other. Powers the `low_limit_set`/`low_limit_reached`/`high_limit_set`/`high_limit_reached` fields on `GET /api/accounts/holdings-list`, and is polled every 5 minutes during market hours by `intraday_orchestrator.py`, which fires a `holding_limit_alert` notification the first time a ticker's live price crosses a stored limit. Scoped to built-in accounts only (`account_id` FK) — a Ghostfolio-only holding has no row to attach a target to. The singleton Watchlist account (`account_type='Watchlist'`) is a valid `account_id` here too — a ticker on the Watchlist (held or not) gets its own "Watchlist" row on the Stock Detail page alongside any real Trading-account rows (the table is generic on `account_id`).
* **Key Columns:** `account_id` (FK to accounts), `ticker`, `low_limit`, `high_limit` (both nullable — either can be set independently of the other; a client sets a column to `NULL` to clear/unset that target, e.g. the Stock Detail page's Position Targets panel treats an empty or `0` input as "clear"), `updated_at`. Stored in the ticker's **native Yahoo units** — for a `GBp` (LSE pence) ticker that is raw pence, matching `current_price`/`stock_signals.current_price`, not GBP pounds — since `intraday_orchestrator._check_holding_limits()` compares the stored value directly against `current_price` with no conversion. The Stock Detail page's input box and the ML Quantile suggestion above it both display/accept **pounds** for a `GBp` ticker (`templates/stock_detail.html`'s `low_display`/`high_display` × 100 on save, `static/js/stock_detail.js`'s `_targetInputValue()` ÷ 100 on prefill) and convert at the UI boundary — saving pounds unconverted would turn the ML-suggested "£6.37" into "£0.06". The Home Assistant integration's Low/High Limit number entities do **no** conversion and simply mirror whatever `market_price_currency` reports, so they round-trip the raw native-unit value as-is.
* **Constraint:** `PRIMARY KEY (account_id, ticker)` — idempotent upsert via `ON CONFLICT DO UPDATE`, only overwriting the column(s) actually supplied so setting one limit never clears the other.
* **CRUD:** `db.account_store.upsert_holding_price_limit()` / `get_all_holding_price_limits()` (batched, all accounts) / `get_holding_price_limits_for_ticker()` (scoped to one ticker, used by the Stock Detail page). `accounts.portfolio_metrics_engine.set_holding_price_limit()` is the caller-facing wrapper used by `POST /api/accounts/holding-price-limit`. SQLite foreign keys are off, so the table itself enforces nothing about `account_id` or `ticker`: `POST /api/accounts/holding-price-limit` (`api.routes_accounts._require_limit_target()`) is the validating boundary — the account must be live and `Trading`/`Watchlist`, and the upper-cased ticker must be an open position (`accounts.accounts_engine.derive_account_holdings()`) or a Watchlist item. Rows written outside this boundary are not rewritten; the intraday scan skips a row whose account is soft-deleted.
* **Notification dedup:** `intraday_orchestrator._evaluate_daily_alert_gate()`/`record_alert_fired()` key on a composite `alert_state.ticker` value `{account_id}:{ticker}:low` / `{account_id}:{ticker}:high` (not a bare ticker symbol), since the same real ticker can independently breach a low and a high target, each needing its own dedup state. HoldingLimit uses a dedicated once-per-UTC-calendar-day gate (fires at most once per key per day, re-arming automatically at the next day's rollover) rather than the shared `_evaluate_alert_gate()` worsened/recovered/cooldown-minutes model every other alert engine uses — a price target is a static threshold the price can legitimately cross back and forth several times in one session, and only the first crossing per day should notify. There is no `NOTIFICATIONS.HOLDING_LIMIT_ALERTS` config block (nothing to tune; the gate is unconditional). Its `NOTIFICATION_SOURCES["holding_limit_alert"]` entry gives it fully independent log-file/in-app/Nextcloud Talk toggles in Settings → Notification Settings, separate from Crash/Moonshot/Anomaly.
* **Scan scope for non-held tickers (e.g. Watchlist-only):** `IntradayOrchestrator._compute_target_only_tickers(held_set, holding_limits_by_ticker)` returns tickers with an active target that aren't in the main portfolio ticker list; `_run()` scans them through `_check_holding_limits()` only, deliberately excluded from `get_portfolio_tickers()` so they never enter Crash/Moonshot/Anomaly evaluation.
* **Workflow Monitor:** the table is the `holding_price_limits` artifact. The manual `Position Targets` node (`JOB_GRAPH["position_targets_source"]`, `non_job`) produces it and consumes `portfolio` and `watchlist_items`, because `POST /api/accounts/holding-price-limit` (the one write path for the Stock Detail box and the Home Assistant Low/High Limit entities) checks the ticker against open positions and the Watchlist. The Crash & Moonshot Alerts job (`intraday_orchestrator_job`) and the MCP Server (`get_ticker_snapshot`) declare it in `consumes`.

#### `account_autotopup_pending`
* **Purpose:** Staging table for the **Auto Top-up** feature (`Trading` accounts only) — the scheduled job (`scheduler_jobs.register_account_topup_job`/`_run_account_topup_job`, dynamic job id `account_autotopup_{id}_job`) never posts a cash deposit directly, since the real bank credit date can drift around weekends/holidays. Instead it inserts a `pending` row here, the account is tagged `[PENDING ACTION]` on `/accounts`, and the account detail page surfaces a confirmation banner. Multiple unresolved rows can stack per account; each is resolved independently rather than the newest replacing or blocking earlier ones.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `scheduled_date` (the date the job fired), `expected_amount` (the configured `autotopup_amount` at fire time), `status` (`pending` | `confirmed` | `dismissed`), `confirmed_amount`/`confirmed_date` (the operator-edited values actually used, set only on confirm), `txn_id` (FK to the `account_transactions` row created on confirm — `NULL` until then or if dismissed), `created_at`.
* **CRUD:** `db/account_store.py` (re-exported from `db/database.py`): `create_pending_topup`, `get_unresolved_pending_topups`, `get_pending_topup`, `resolve_pending_topup`. Confirm/dismiss logic lives in `accounts.accounts_engine.confirm_autotopup()`/`dismiss_autotopup()` — confirming posts a `Cash` transaction (`update_cash=True`) for the edited amount/date; dismissing never touches `account_transactions`.
* **Scheduling:** one dynamic APScheduler job per scraper-enabled account (`account_scraper_{account_id}_job`, registered/unregistered by `scheduler_jobs.register_account_scraper_job`/`unregister_account_scraper_job`), at the account's own `scrape_time` in `USER_TIMEZONE` — configured from the Accounts page tile/detail page, not the Settings page. See `scheduler_manifest.JOB_GRAPH["account_scraper_dynamic"]`.

#### `account_reminders`
* **Purpose:** Pension Reminders configuration (`Pension` accounts only) — one row per reminder, several per account.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `reminder_type` (`pay_in` | `admin_fee`), `cadence` (`monthly`, the only value), `day_of_month` (1-31; 29-31 fall on the last day of a shorter month), `enabled` (default 0), `created_at`.
* **CRUD:** `db/account_reminders.py`. Validation lives in `accounts.account_reminders_engine.reminder_error()`.
* **Scheduling:** one dynamic APScheduler job per enabled reminder (`account_reminder_{id}_job`, 08:00 in `USER_TIMEZONE`; registered/unregistered by `scheduler_jobs.register_account_reminder_job`/`unregister_account_reminder_job`, re-registered at startup, matched in the manifest via `scheduler_manifest._DYNAMIC_ACCOUNT_REMINDER_RE`). A day of 29-31 uses an `OrTrigger` of the day itself and `day="last"` for the months that lack it.

#### `account_reminder_pending`
* **Purpose:** Staging table for Pension Reminders. The job never records a transaction; it inserts a `pending` row, the Pension tile is tagged `[PENDING ACTION]`, and the Pension account page lists what is waiting. Rows from several months stack and are resolved independently. A pending row carries its own `reminder_type`, so deleting or disabling the reminder leaves it in place.
* **Key Columns:** `id` (PK autoincrement), `reminder_id`, `account_id`, `reminder_type`, `due_date` (local date in `USER_TIMEZONE` the job fired; names the month in the title, e.g. "November 2026 Pay In"), `status` (`pending` | `done` | `dismissed`), `txn_id` (the Pay In / Admin Fee transaction when `done`), `resolved_at` (UTC), `created_at`. `UNIQUE (reminder_id, due_date)` makes a double fire a no-op.
* **CRUD:** `db/account_reminders.py`; `accounts/account_reminders_engine.py` holds the title, validation, dismissal and job-side staging logic. `POST /pension/contribution` and `/pension/fee` mark a row `done` when given its `reminder_pending_id`.
* **Workflow Monitor:** the table is the `account_reminder_pending` artifact. The dynamic `Pension Reminders` job nodes produce it and the `Pension Account(s)` node consumes it.

#### `treasury_bills`
* **Purpose:** Tracks UK Treasury bill holdings (`Trading` accounts only) — zero-coupon instruments bought at a discount to face value with no coupon, maturing at par roughly 28 days later. One row per purchase. Each bill's Buy leg is posted to `account_transactions` against a unique synthetic ticker (`TBILL-{buy_txn_id}`), so concurrently-held bills never blend cost basis in `_ledger_for_account`'s average-cost math the way a shared ticker would.
* **Key Columns:** `id` (PK autoincrement), `account_id` (FK to accounts), `buy_txn_id` (FK to the `account_transactions` Buy row), `ticker` (`TBILL-{buy_txn_id}`, `UNIQUE`), `face_value` (par/maturity value — see note below on how this is derived), `purchase_price` (discount price actually paid — always `< face_value`), `indicative_ytm` (nullable — the annualised yield shown in the app at purchase time; overwritten with the real confirmed rate once the operator confirms it, see below), `ytm_confirmed` (bool, default `0` — whether the operator has confirmed/accepted the YTM since the Friday tender closed; `1` immediately if no `indicative_ytm` was given at purchase, since there's then nothing to confirm), `purchase_date`, `maturity_date`, `auto_reinvest` (bool — a reminder-only flag, see below), `status` (`Open` | `Matured`), `maturity_txn_id` (FK to the `account_transactions` Sell row posted at maturity, `NULL` until then), `notes`, `created_at`.
* **No `currency` column** — always derived from the linked account at read time (one canonical source, per the codebase's "never duplicate a shared calculation" rule).
* **`face_value` starts as an estimate, editable any time it turns out wrong:** Freetrade never states a bill's face value directly — only the amount debited and an indicative, pre-tender yield (the real yield for a specific bill isn't fixed until the Friday DMO tender closes, which can be after the bill is already logged in this app). The Buy T-Bill modal computes `face_value = purchase_price + purchase_price × indicative_ytm × days/365` (`accounts.treasury_bill_engine.estimate_face_value()`) and pre-fills it as an editable field. Once `purchase_date` (the settlement date, always after that Friday's tender) has arrived, an unconfirmed bill surfaces a "Confirm the final YTM" banner on the account page (`accounts.treasury_bill_engine.bills_pending_ytm_confirmation()`, mirroring the Auto Top-up confirm/dismiss pattern); entering the real rate recomputes `face_value` with the same formula, and "Keep Estimate" just clears the banner unchanged — both via `accounts.treasury_bill_engine.confirm_ytm()`. That same function backs a general **Edit** action available on every bill's row at any time, Open or already Matured — accepting either a `confirmed_ytm` to recompute from, or a `face_value` directly (if the operator knows the exact redemption figure without needing a rate). **Editing a Matured bill also corrects its posted maturity Sell transaction's amount to match**, since that transaction — not the `treasury_bills` row — is what the account's cash balance actually derives from; without this, an edit after maturity would silently desync the two.
* **Pricing:** `accounts.treasury_bill_engine.accreted_price()` computes a deterministic straight-line value between `purchase_price` (at `purchase_date`) and `face_value` (at `maturity_date`) — no external price feed needed, unlike the Pension/House synthetic-holding pattern's `account_price_history`. `accounts.accounts_engine.current_price_map()` dispatches any `TBILL-%` ticker to this function (mirroring the existing `PENSION-%` branch), so `holdings_with_market_value`, `portfolio_totals`, and the Home Assistant `holdings-list` endpoint all show the accreting value automatically. `accounts.accounts_engine.backfill_value_history()` (used for `account_value_history` rows predating the account's live-snapshot history) resolves the same `TBILL-%` tickers the same way — a `TBILL-%` ticker has no parquet file, so without this dispatch it would fall back to flat cost basis on every backfilled snapshot instead of the accreted value, understating a held bill's value on any historical date. The same accretion math also backs the Home Assistant `holdings-list` endpoint's `asset_class` (fixed to `"Fixed Income"`) and `market_change_24h`/`market_change_pct_24h` (`accounts.treasury_bill_engine.daily_accretion_change()` — today's `accreted_price()` minus yesterday's) fields for TBILL rows — both would otherwise be `null` since synthetic TBILL tickers never get a `stock_signals` or `market_pulse_cache` row (see the "Excluded from Yahoo fetch machinery" bullet below).
* **CRUD:** `db/account_store.py` (re-exported from `db/database.py` where used by the API layer): `create_treasury_bill`, `get_treasury_bill`, `get_treasury_bill_by_ticker`, `get_treasury_bills_for_account`, `get_open_treasury_bills_due`, `mark_treasury_bill_matured`, `update_treasury_bill_auto_reinvest`, `get_treasury_bills_pending_ytm_confirmation`, `confirm_treasury_bill_ytm`, `delete_treasury_bill`. Purchase/maturity/confirmation/deletion logic lives in `accounts/treasury_bill_engine.py`.
* **Scheduling:** the always-on daily `treasury_bill_maturity_sweep_job` (`accounts.treasury_bill_engine.sweep_matured_bills`, runs 07:00 in `USER_TIMEZONE`, no Settings toggle — a matured position must never sit open corrupting cash/holdings) posts the maturity `Sell` transaction for any bill whose `maturity_date` has arrived, crediting the account's cash balance with `face_value`. If `auto_reinvest` is set, it fires a `notification_engine.notify("treasury_bill_reminder", ...)` reminder — **never an automatic re-purchase**, since the actual yield on the next weekly DMO tender isn't known until the Friday it closes. The YTM-confirmation banner, by contrast, is a plain page-render-time check (`purchase_date <= today AND ytm_confirmed=0`) — no separate scheduled job or notification, since the bill row already exists in full from the moment of purchase.
* **Excluded from Yahoo fetch machinery:** `db.account_store.get_all_account_tickers()`, `accounts.accounts_engine.held_tickers_lightweight()`, `data_engine.DataEngine.get_all_tickers()` (the main nightly fetch universe), and `intraday_orchestrator.IntradayOrchestrator.get_portfolio_tickers()` (the 5-minute Crash/Moonshot scan's bulk fetch) all exclude `TBILL-%` tickers, the same way they exclude `PENSION-%` — the latter exclusion is load-bearing here in a way it wasn't for Pension, since T-bill tickers live inside ordinary `Trading` accounts rather than a dedicated account type. Without the exclusion, every T-bill would produce a guaranteed-failing "possibly delisted" Yahoo request on every nightly fetch and every 5-minute scan tick — harmless to data correctness (the accreted analytical price is unaffected) but constant log noise and wasted requests. All of them dispatch through the same `accounts.treasury_bill_engine.parse_tbill_buy_txn_id()` check used by `current_price_map()`'s live-pricing dispatch and `backfill_value_history()`'s historical dispatch, rather than independent prefix checks.

### Stateless Tools (no DB table)

#### Historical Stress Tester (`stress_engine.py`)
Results are computed on-demand and returned directly in the API response — **no table is written**. The engine reads per-ticker beta from `xray_risk_cache` and holdings from Ghostfolio's live API, applies pre-calibrated scenario shocks, and returns the monetary impact report. Run the X-ray nightly job first to ensure `xray_risk_cache` is populated with up-to-date betas.

#### Portfolio Optimizer (`portfolio_optimizer_engine.py`)
Results are computed on-demand and returned directly in the API response — **no table is written**, same as the Monte Carlo Wealth Simulator and Portfolio Tearsheet above. Min-Variance/Max-Sharpe weights are closed-form `numpy` matrix algebra in Unconstrained mode and `scipy.optimize.minimize(method="SLSQP")` solves in Long-Only mode (Weight Cap bounds, Cash Reserve budget; no `cvxpy` dependency), alongside an Equal Weight Mix baseline, over a per-ticker base-currency returns matrix (native returns compounded with dated FX by `fx_conversion_helpers`) read from `xray_returns_cache` (held tickers) with a direct parquet fallback (`xray_engine.fetch_close_returns_from_parquet`) for candidate tickers that have never been held — e.g. an opted-in Watchlist ticker, which the nightly X-ray precompute never populates into `xray_returns_cache`.

## 5. Scheduler Job Dependency Map (Workflow Monitor)

The Workflow Monitor (Settings UI) does not store a graph in the database — it is derived at request time from a **declarative manifest plus live state**. The scheduler subsystem is split across four modules (all re-exported from `scheduler_engine` for backward compatibility):

| Module | Responsibility |
|---|---|
| `scheduler_engine.py` | APScheduler setup, `start_scheduler`, `reload_scheduler`, job wiring + tracking infrastructure |
| `scheduler_jobs.py` | All `run_*` job runner functions + `resume_interrupted_scans` |
| `scheduler_manifest.py` | `JOB_GRAPH`, `CONFIG_KEY_TO_JOB`, `job_label()`, `scheduler_display_names()`, `_resolve_manifest()` |
| `scheduler_monitor.py` | `build_workflow_graph()`, `detect_workflow_conflicts()` |

* **`JOB_GRAPH`** (`scheduler_manifest.py`): one entry per `scheduler.add_job(... id=X)`. Each entry declares the data **artifacts** a job reads (`consumes`) and writes (`produces`) — e.g. `quant_signals`, `ml_model`, `ml_predictions`, `historical_parquet`, `portfolio`, `sentiment`. Dynamic per-config jobs (ETF predictors, and the per-account Account Price Scraper jobs — `account_scraper_{account_id}_job`, matched via `_DYNAMIC_ACCOUNT_SCRAPER_RE`) are matched in `_resolve_manifest()`.
* **Edges** are derived, never hand-listed: a dependency `A → B` exists iff `A.produces ∩ B.consumes ≠ ∅`. Adding a job with correct declarations auto-wires it into the graph.
* **Live overlay:** `build_workflow_graph()` (`scheduler_monitor.py`) merges the manifest with `scheduler.get_jobs()` (enabled? next run?) and `scheduler_run_log` (last run, average duration, last status) to colour each node and compute conflicts. Individual executions remain in `scheduler_run_history` for the Settings Master APScheduler Matrix detail window.
* **Conflict engine** (`detect_workflow_conflicts()` in `scheduler_monitor.py`): `overlap_risk` (consumer scheduled within the producer's average run duration), `backwards_ordering`, `disabled_upstream`, `stale_never_run`, `last_run_error`.
* **Enforcement:** the manifest-completeness test fails CI if any registered job lacks a `JOB_GRAPH` entry, keeping the map in sync with the scheduler automatically.

### Persisted FX quotes in `market_pulse_cache`

`fx_rate REAL` and `fx_updated_at REAL` store the last-successful FX conversion quote and its UTC epoch fetch timestamp per Yahoo currency-pair ticker. `db.schema.init_db()` creates the fields and `migrate_db()` adds them idempotently to existing installations. `db.helpers.upsert_fx_quote()` updates only these fields on an existing pulse row, preserving live-price/session metadata; a new row starts with the fetched price and timestamp as well. A failed fetch does not write either field. Successful FX pulse writers also call this helper, and `get_cached_fx_quote()` can reuse the newest direct or reciprocal snapshot. Ordinary pulse heartbeat timestamps are never used as successful-FX timestamps. Navigation applies the age limits from `PERFORMANCE` in `config.json`; restart preserves the original age. No historical transaction FX or time-series storage changes are made.
